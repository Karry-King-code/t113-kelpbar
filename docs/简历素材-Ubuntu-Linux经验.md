# 0. 三条浓缩版（简历直接用，与"丢包攻关"同格式）

> 格式：**四字标题**：定位 → 做法 → 结果。三条分别对应 **性能优化 / 硬件适配广度 / 协议排障深度**。

• **带宽攻关**：定位蓝牙音频卡顿（8 秒字节计数对账锁定 10.2/41KB/s 管道瓶颈），采用 sink 协商码率收窄方案（单声道+bitpool10）解决，并修复 force-mono 仅作用于 source 的隐藏缺陷

• **板级移植**：定位官方 BSP 与实板硬件错配（原理图与内核引脚表双证锁定串口/触摸引脚），采用引导参数与设备树修正方案完成九类外设适配，并修复幽灵节点遮蔽触摸驱动的隐藏缺陷

• **协议打通**：定位手机连板放歌失败（btmon 抓包锁定五层阻断），采用服务补注册+删配对重配方案解决，并修复 BlueZ 不生成音频 SDP 记录的隐藏缺陷

> **面试展开顺序**：先说"带宽攻关"（有 10.2/41 这组数字，最能证明量化能力），再按追问展开另外两条。

# 3. STAR 故事（面试口述用，每个 60–90 秒）

## 3.1 故事一：带宽算账（最推荐，展示量化思维）

- **S**：手机连开发板当蓝牙音箱，能连上但放歌严重卡顿。
- **T**：找出卡顿根因并解决。
- **A**：先量化再动手——用 `hciconfig` 的 RX 字节数做 8 秒差值，测得链路实际吞吐 **10.2 KB/s**；查 SBC 编码资料得立体声需求约 **41 KB/s**，判断是管道容量只有需求的 1/4，数据饿死。排查内核 overrun 与 HCI 错误计数均为 0，排除驱动层。先尝试提高芯片串口波特率（1.5M），编码正确但固件下载超时且芯片会假死，果断放弃；改用降低流量：读 bluealsa 源码发现其单声道参数只作用于 source 端、对 sink 无效，于是修改 `src/a2dp.c` 让 sink 只广播单声道与低 bitpool，手机按 A2DP 规范只能在范围内选择，码率从 12 降到 10，流量约 8 KB/s，留 20% 余量。
- **R**：播放流畅，用户验收；代价是音质降至"电话音质"，是在 10 KB/s 管道下的理性取舍。验证只认 `btmon` 抓包里的协商参数，不认体感。

## 3.2 故事二：五层洋葱（展示排查深度）

- **S**：手机蓝牙"已配对"但连不上音箱，反复重试无效。
- **T**：定位为什么配对成功却不能连接。
- **A**：用 `btmon` 抓包逐层排除，五层不同根因：①板子缺配对应答程序（日志 `Authentication attempt without agent`）；②应答程序能力声明错误（被工具自动注册的 KeyboardDisplay 覆盖），手机报"PIN 码不正确"实为 30 秒无人确认超时；③音频端点注册丢失；④对端缓存了配对时的服务快照，板子事后补注册它不知道；⑤BlueZ 兼容模式的已知问题，音频 SDP 记录不自动生成，需手动 `sdptool add A2SNK`。
- **R**：全部修复后手机显示"已连接到媒体音频"并正常播放。沉淀出可复用规律：**对端的功能列表是配对那一刻的快照，必须"先修服务、再删配对重配"**。

## 3.3 故事三：查源码纠正自己的结论（展示严谨）

- **S**：内核配置按经验加了若干开关，其中按键功能仍然异常。
- **T**：确认到底是哪个开关在起作用。
- **A**：没有继续"多试几个"，而是去内核源码查证：`grep 'config GPIO_KEYS' drivers/input/` 零输出——这个符号根本不存在，写进配置被静默丢弃；真正需要的是 `CONFIG_KEYBOARD_GPIO`，其 Kconfig 只依赖 `GPIOLIB`。
- **R**：纠正了长期沿用的错误归因，并把"查 Kconfig 验符号与依赖"固化为方法。

## 3.4 备选故事：无屏验证（展示工程巧思）

屏幕硬件暂缺时，先把 LVGL 移植完：把 `/dev/fb0` 显存整块 dump 回来，按 720×1424×32bpp（BGRA）解码成图片，验证图形界面渲染正确；再用文件描述符与 CPU 时间确认显示/触摸通路接入。换屏后零改动直接显示。

# 4. 面试问答预演（针对简历可能被追问的）

| 追问 | 怎么答 |
|---|---|
| "你说的板级适配具体做什么？" | 官方 BSP 配的是评估板，我们的板硬件接线不同（串口脚、触摸总线、WiFi 芯片都不同），我的工作是改配置让软件匹配实际硬件，并逐项验证 |
| "交叉编译怎么做的？" | Ubuntu 里把 ARM 工具链加入 PATH、设 STAGING_DIR 指向目标库，Makefile 传 `CC=arm-openwrt-linux-gcc`，产物用 `file` 确认 ARM 架构；蓝牙音频那次的补丁就是这么重编部署的 |
| "设备树是什么？" | 描述硬件的配置，内核靠 compatible 字符串匹配驱动并调用 probe；同一内核跑不同板，板间差异都在设备树 |
| "遇到最难的问题？" | 讲 3.1 带宽算账 |
| "怎么保证验证可信？" | 讲"命令没报错≠功能正常"，举录音看峰值/RMS、显示先查分辨率数字、蓝牙只认抓包协商参数 |
| "你写过驱动吗？" | **诚实**："没有从零写过字符设备驱动，我做的是驱动适配与配置——准确理解设备树、probe、中断下半部这些机制，但手写驱动是我下一步要补的" |
| "会 ROS2 吗？" | "正在学，已了解话题/服务/动作、DDS 与 QoS 概念；我 Linux 底层的经验能直接迁移" |

# 5. 简历上"Ubuntu 经验"的正确写法

**不要写**："熟练使用 Ubuntu"（太虚）。
**要写**：把 Ubuntu 作为**工作环境**体现在具体动作里——

- "在 Ubuntu 环境下配置 ARM 交叉编译工具链与 SDK，完成内核/设备树的编译、打包与烧录"
- "使用 SSH 远程操作 Ubuntu 编译机，编写 Shell/Python 脚本自动化部署与验证"
- "在 Ubuntu 中基于源码修改开源协议栈（bluealsa）并交叉编译部署到目标板"

这三句比"熟悉 Ubuntu"有信息量得多，而且每句你都能展开讲。
