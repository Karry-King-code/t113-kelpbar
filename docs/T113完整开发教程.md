| 存储 | W25N01GV **SPI NAND 128MB** | 固件烧在这里 |
| 内存 | **DDR3 128MB**（内置） | |

## 0.3 三窗口工作法（第一天就要建立的意识）

整个项目你会同时面对**三个终端**，敲错窗口是新手第一大坑：

| 终端 | 提示符长这样 | 干什么 |
|---|---|---|
| **VM 终端**（虚拟机里 Ubuntu） | `karry@karry-VirtualBox:~$` | 改代码、编译、打包 |
| **Windows 终端** | `C:\Users\XYT>` | adb 推文件/敲板子命令、开串口终端 |
| **板子终端**（串口或 adb 进入） | `root@TinaLinux:/#` | 看板子状态、验证功能 |

> ### ★ 方法论二：敲命令前先看提示符
> 把板子命令敲进 VM 终端，输出全是虚拟机自己的设备——会让你以为板子坏了。
> **每个终端的能力不同**：`amixer` 只有板子有，`adb` 只有 Windows 有，`build.sh` 只有 VM 有。

## 0.4 全书的世界观：什么叫"移植"

这块板的官方 BSP（板级支持包）是全志给**评估板**做的，评估板的硬件配置和本板**不一样**（调试串口在 PG8/PG9、触摸挂在 twi2、WiFi 芯片是 XR829……）。

> **移植 = 让软件配置匹配实际硬件。**
> 官方配置是给评估板的；你的板子硬件不一样，就必须改软件配置去匹配它。
> —— 这是全书的主题，每一关都是这个主题的变奏。

# 第 2 章 · BSP、编译与烧录（贯穿性知识）

> 这一章是"内功"。第 3 章开始每一关的改动，全部落在这一章讲的几个文件里。

## 2.1 什么是 BSP，SDK 里都有什么

**BSP（Board Support Package，板级支持包）**= 让一套系统跑在**某块具体板子**上的全部配置：引脚怎么接、总线怎么开、驱动选哪些。

Tina SDK 关键目录地图（本教程用到的）：

```
~/T113-Tina5.0-V1.2/
├── device/config/chips/t113/configs/evb1_auto_nand/   ★ 板级配置目录（最常来）
│   ├── sys_config.fex          引导期（U-Boot）配置
│   ├── openwrt/env.cfg         内核启动参数（console、initcall_debug…）
│   └── linux-5.4/
│       ├── board.dts           内核设备树（注意可能是软链接！）
│       └── config-5.4          内核 Kconfig 配置
├── openwrt/openwrt/target/linux/t113-common/modules.mk   KernelPackage 定义
├── openwrt/target/t113/t113-evb1_auto_nand/
│   ├── defconfig               Tina 包选择（rootfs 装什么）
│   └── base-files/etc/         ★ 会打进固件的 /etc（rc.local、自启脚本放这里）
├── out/t113/.../               编译产物（内核、rootfs、build 目录）
└── out/t113_linux_evb1_auto_nand_uart0.img   ★ 最终烧录镜像
```

## 2.2 ★ 三个配置层的区别（改错文件 = 白干）

| 文件 | 管什么 | 举例 |
|---|---|---|
| `linux-5.4/config-5.4` | **内核**功能开关 | `CONFIG_KEYBOARD_GPIO=y` |
| `t113-evb1_auto_nand/defconfig` | **rootfs 装哪些包** | `CONFIG_PACKAGE_kmod-net-8723ds=y` |
| `t113-common/modules.mk` | 内核模块 ↔ 包的**映射** | 8723ds.ko 打进哪个 kmod 包 |
| `board.dts` | **硬件描述**（引脚/总线/外设） | 触摸挂哪个 I2C、LED 在哪个脚 |
| `env.cfg` | **启动参数** | 控制台口、initcall_debug |
| `sys_config.fex` | **引导期**（boot0/U-Boot）配置 | 调试串口引脚 |

**一句话**：内核功能去 `config-5.4`，装什么软件去 `defconfig`/`modules.mk`，硬件怎么接去 `board.dts`，启动行为去 `env.cfg`/`sys_config.fex`。

## 2.3 编译与打包（固定三连）


**拉回 Windows**：


## 2.4 ★ 改动落盘三定律（血的教训换来的）

| # | 定律 | 为什么 |
|---|---|---|
| 1 | **改"真身"，不用 `sed -i` 碰软链接** | `sed -i` 修改软链接时会销毁链接、原地生成普通文件——你 `cat` 验证的是新文件，编译读的是原版真身，**验证和编译读的是两个文件**（第 3 章详解） |
| 2 | **板上写完文件必须 `sync`** | 写入先落 page cache，不 `sync` 直接断电 = 文件丢失甚至变 0 字节（蓝牙关踩过：`/etc/bt_up.sh` 被清零导致开机静默跳过蓝牙） |
| 3 | **开机自启的东西放 SDK 的 `base-files/etc/`** | 只改板上 `/etc`，重烧就被清空；放进 SDK 的 `base-files/etc/` 才会**每次打进固件**；板上 `/root` 留双份互备 |

# 第 3 章 · 调试串口：看到系统的心跳

> **目标**：串口打印完整启动日志，能进 shell。
> **为什么第一关是它**：板子黑屏、不启动、卡死时，串口是**唯一能看到真相的通道**。后面每一关的排障全靠它。
> **详细逐条命令版**：[01-serial/README.md](../01-serial/README.md)

## 3.1 硬件事实（有据版）

| 项目 | 值 | 证据 |
|---|---|---|
| 调试串口 | UART3，TX=PB6 / RX=PB7，U24 三针座 | 原理图第 1 页（下图） |
| 参数 | 115200-8N1 | 与 boot0/U-Boot/内核默认一致 |
| PB6=UART3-TX | 功能号 `<7>` | **数据手册 GPIO 复用表** + 内核 C 表 `pinctrl-sun8iw20.c` 双重验证 |

原理图上的调试口（U24 三针座，UART3_TX/RX 经 ESD 保护到座子）：

![UART3 调试口原理图特写](images/SCH_UART3调试口特写.png)

数据手册的 GPIO 复用表（Table 5-3 GPIO Multiplex Function）里查 PB6/PB7 行：PB6 的 Function7 = UART3-TX、PB7 的 Function7 = UART3-RX：

![数据手册 PB6 复用行](images/DS_PB6_UART3TX复用.png)

![数据手册 PB7 复用行](images/DS_PB7_UART3RX复用.png)

> **深挖：功能号 `<7>` 是怎么定的？**
> 设备树/配置里引脚后面尖括号里的数字是**复用功能号**。同一根引脚在不同功能号下是不同外设（PB6 可以是 GPIO、LCD 数据、UART3……）。
> **权威是内核 C 表**（规律：数据手册 FunctionN 列 = 内核功能号 0xN，PB6 手册 Function7=UART3-TX ↔ 内核 `0x7="uart3"`）：
> ```sh
> grep -n -A8 'PINCTRL_PIN(B, 6)' \
>   ~/T113-Tina5.0-V1.2/kernel/linux-5.4/drivers/pinctrl/sunxi/pinctrl-sun8iw20.c
> # ⚠️ C 表引脚名是宏写法 PINCTRL_PIN(B, 6)，直接搜 "PB6" 搜不到
> # 看到 SUNXI_FUNCTION(0x7, "uart3") /* TX */ → 填 <7>
> # 交叉验证：PINCTRL_PIN(G, 8) 的 0x5 = "uart3"，与评估板配置 <5> 吻合 → 方法闭环
> ```

## 3.2 问题：为什么官方镜像串口一个字都没有

官方 BSP 的调试口配在评估板的 **PG8/PG9**，本板的调试线接在 **PB6/PB7**——配置和硬件对不上，日志发到了一个没人听的脚上。**这就是第一章说的"移植"最典型的案例。**

**要改三处**（分别管三个启动阶段，缺一不可）：

> ### ★ 先搞清楚"查哪里 → 去哪改"
> 本关 4 个文件：**1 个只查不改（字典），3 个要改**。板子启动分两段，两段各读一套配置——
> 引导期只认 `sys_config.fex`（全志私有 FEX 格式，**不是设备树**），内核期只认 `board.dts`（设备树），
> `env.cfg` 是内核驱动加载前最早打印（earlycon）用的寄存器地址。**少改任何一处 = 日志断一段。**
> 功能号 `<7>` 来自查"字典" `pinctrl-sun8iw20.c`（内核 pinctrl 驱动源码，只查不改）——见下方深挖。

| 文件 | 身份 | 管哪个阶段 | 改什么 |
|---|---|---|---|
| `openwrt/env.cfg` | 内核启动参数 | 内核刚解压（earlycon） | 串口寄存器地址 `0x05000000` → `0x02500C00` |
| `sys_config.fex` | 全志引导配置（非设备树） | 引导期（U-Boot） | `port:PG08<5>/PG09<5>` → `port:PB06<7>/PB07<7>` |
| `linux-5.4/board.dts` | **设备树** | 内核期 | `pins = "PG8","PG9"` → `"PB6","PB7"`（**有两处，sed 要加 `g`**） |

关键命令（VM 里，目录太长先 `cd` 进去再操作）：

```sh
cd ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand
cp openwrt/env.cfg openwrt/env.cfg.bak-serial
sed -i 's/0x05000000/0x02500C00/' openwrt/env.cfg

sed -i 's/port:PG08<5>/port:PB06<7>/' sys_config.fex
sed -i 's/port:PG09<5>/port:PB07<7>/' sys_config.fex

# board.dts 必须改真身（见 3.3）
cp linux-5.4/board.dts linux-5.4/board.dts.bak-serial
sed -i 's/pins = "PG8", "PG9"/pins = "PB6", "PB7"/g' linux-5.4/board.dts
sed -n '410,430p' linux-5.4/board.dts     # 眼见为实
```

改完 → `./build.sh && pack` → 烧录 → 串口终端应看到：

```
HELLO! BOOT0 is starting!
U-Boot 2018.07-...
Linux version 5.4.61 ...
Please press Enter to activate this console.
root@TinaLinux:/#        ← 进 shell，串口完成
```

## 3.3 ★ 本关最重要的坑：软链接陷阱

**现象**：改了 `board.dts`，`cat` 验证明明改对了，重编重烧后**改动死活不生效**。

**真因**：`~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/board.dts` 是个**软链接**，真身在 `linux-5.4/board.dts`。GNU `sed -i` 修改软链接时会**销毁链接、在原地生成一个普通文件**：

```
改之前：  board.dts --(软链接)--> linux-5.4/board.dts（真身）
sed -i 后：board.dts（普通文件，你的改动在这里）
           linux-5.4/board.dts（真身，一字未改！）
```

随后 `./build.sh` 发现布局被破坏，删掉那个普通文件、重建软链接指回原版。结果：**你验证读的是新文件，编译读的是真身——平行线永不相交。**

**正确做法**：① 一律改真身 `linux-5.4/board.dts`；② 或用 Python 脚本（`open()` 穿透软链接）；③ 绝不用 `sed -i` 直接碰软链接。改完必查：`ls -la linux-5.4/board.dts`，mtime 应该是刚刚。

## 3.4 排查范式：内核"精确卡死"用 initcall 照妖镜

**现象**：内核启动到某一处精确卡死，16 秒后看门狗复位，循环。**每次卡在同一行**（确定性卡死；手按复位是随机位置——用这一点区分两者，用证据判定，不靠猜）。

**工具**：`initcall_debug`。内核启动会逐个执行驱动初始化函数，打开开关后每个函数执行前后都打印：

```
calling  xxx_init+0x0/0x100
initcall xxx_init+0x0/0x100 returned 0 after 1234 usecs
```

**凶手 = 最后一个只有 `calling` 没有 `returned` 的驱动。**

```sh
# 打开开关（改 env.cfg，只需 pack 不用重编）
sed -i 's/initcall_debug=0/initcall_debug=1/' ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/openwrt/env.cfg
```

本项目实测抓到的凶手：`calling deferred_probe_initcall` 后无下文，搜 `-517`（EPROBE_DEFER，内核的"补考机制"）找到 `probe of 2502c00.twi returned -517`——**twi3 是空总线却开着 status="okay"**，补考时 I2C 传输死等不超时。修法：带行号精准改 `disabled`（**不能全局替换 status**，spi0 上挂着启动必需的 NAND，关错=板子变砖）。

## 3.5 验证关卡与踩坑档案

| # | 检查项 | 期望 |
|---|---|---|
| 1 | 串口有输出 | `HELLO! BOOT0 is starting!` |
| 2 | 内核版本行 | `Linux version 5.4.61 ...` |
| 3 | 控制台就绪 | `Please press Enter to activate this console.` |
| 4 | 能进 shell | `root@TinaLinux:/#`，系统稳定不复位 |

踩坑速查：乱码=波特率不对；串口突然没输出=COM 口重新枚举换了号（看设备管理器）；Enter 没反应=要等提示出现再按（且脚本要发 `\r\n`），或直接走 adb。

## 4.2 第一步：内核开关（最容易漏的一步）

> ### ★ 先说清改哪里、为什么改这里（本关只动两个文件）
>
> | 文件 | 完整路径 | 改它干什么 | 为什么是它 |
> |---|---|---|---|
> | 内核配置 | `~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/config-5.4` | 追加 6 个 `CONFIG_* =y` | 它决定**哪些驱动编进内核**。gpio-leds / gpio-keys 驱动代码内核自带，但默认没编进去——开关在这里打开 |
> | 设备树 | 同目录 `board.dts`（改真身） | 追加 leds / gpio-keys 两个节点 | 它决定**驱动管哪块硬件**。LED 接 PD11、按键接 PD10 这种接线事实，写成节点"登记"给驱动 |
>
> 一句话分工：**config 开功能（把驱动装进来），dts 接硬件（告诉驱动去管谁）。** 少任何一个：
> 只开 config 不写 dts = 驱动在但没有设备可管；只写 dts 不开 config = 节点成了"没人认领的孤儿"。

先侦察（VM 里）：

```sh
grep -nE 'GPIO_SYSFS|LEDS_GPIO|GPIO_KEYS|NEW_LEDS|LEDS_CLASS|KEYBOARD_GPIO' \
  ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/config-5.4
# 零输出 = 全没开
```

**要开 6 个，不是 3 个**——内核配置有**依赖链**，父开关不开子开关无效：

| 开关 | 角色 |
|---|---|
| `CONFIG_NEW_LEDS` | LED 子系统框架（**父开关**） |
| `CONFIG_LEDS_CLASS` | LED 类设备（中间层） |
| `CONFIG_LEDS_GPIO` | GPIO LED 驱动（功能本体） |
| `CONFIG_GPIO_SYSFS` | GPIO 用户态接口 |
| `CONFIG_GPIO_KEYS` | 按键子系统杂项 |
| **`CONFIG_KEYBOARD_GPIO`** | **gpio-keys 驱动本体（★ 最容易漏）** |

> **名字陷阱**：`GPIO_KEYS` 和 `KEYBOARD_GPIO` 长得像，作用完全不同。只开前者不开后者 → dts 节点成了"没人认领的孤儿"，按键毫无反应。本项目当时就是"LED 亮但按键没反应"这个**不对称现象**才锁定它。
>
> **方法论三：内核配置被静默丢弃 = 依赖不满足。** 沿 `depends on` 一路挖到底。

```sh
cd ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4
cp config-5.4 config-5.4.bak-gpio
cat >> config-5.4 << 'EOF'
CONFIG_NEW_LEDS=y
CONFIG_LEDS_CLASS=y
CONFIG_LEDS_GPIO=y
CONFIG_GPIO_SYSFS=y
CONFIG_GPIO_KEYS=y
CONFIG_KEYBOARD_GPIO=y
EOF
grep -cE 'CONFIG_NEW_LEDS|CONFIG_LEDS_CLASS|CONFIG_LEDS_GPIO|CONFIG_GPIO_SYSFS|CONFIG_GPIO_KEYS|CONFIG_KEYBOARD_GPIO' config-5.4   # 期望 6
```

## 4.3 第二步：设备树节点（逐行讲）

```sh
cd ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4
cp board.dts board.dts.bak-led
cat >> board.dts << 'EOF'

/ {
	leds {
		compatible = "gpio-leds";
		led1 {
			label = "kelpbar:led1";
			gpios = <&pio 3 11 GPIO_ACTIVE_HIGH>;
			default-state = "off";
		};
	};

	gpio-keys {
		compatible = "gpio-keys";
		btn1 {
			label = "kelpbar:btn1";
			gpios = <&pio 3 10 GPIO_ACTIVE_LOW>;
			linux,code = <115>;
			wakeup-source;
		};
	};
};
EOF
```

| 字段 | 含义 |
|---|---|
| `compatible` | **自我介绍**：内核靠这个字符串匹配驱动。`"gpio-leds"` 对应 leds-gpio 驱动，`"gpio-keys"` 对应 gpio-keys 驱动 |
| `gpios = <&pio 3 11 极性>` | 控制器 + 组号 + 脚号 + 有效电平 |
| `linux,code = <115>` | 按键上报的键码，115=KEY_VOLUMEUP，**随便选合法键码即可** |
| `wakeup-source` | 可作唤醒源 |

> **为什么按键一行中断代码都不用写？** gpio-keys 驱动**内置**了中断、去抖、事件上报。你只在设备树里"登记"，驱动自己干活——**Linux 驱动的哲学：配置代替编码**。

## 4.4 编译验证三件套

编完烧录后（板子终端）：

```sh
# ① LED：注册了吗 / 亮了吗
ls /sys/class/leds/                                       # 见 kelpbar:led1
echo 255 > /sys/class/leds/kelpbar:led1/brightness        # 灯亮
echo 0 > /sys/class/leds/kelpbar:led1/brightness          # 灯灭

# ② 按键：注册了吗（★ 设备名是驱动名 gpio-keys，不是 label！）
grep -A5 gpio /proc/bus/input/devices                     # Name="gpio-keys" + event4
cat /dev/input/event4                                     # 按住 BTN1 → 刷二进制流（正常）

# ③ 终极真相：GPIO debugfs（直接读硬件寄存器状态）
mount -t debugfs none /sys/kernel/debug 2>/dev/null
cat /sys/kernel/debug/gpio | grep kelpbar
# gpio-106 (kelpbar:btn1) in  hi IRQ ACTIVE LOW   ← IRQ 挂上了、低有效
# gpio-107 (kelpbar:led1) out lo
```

按键事件的结构（hexdump 翻译，16 字节一个事件）：

```
01 00 73 00 01 00 00 00
│  │  │  │  └──┴─ value=1 按下
│  │  └──┴─ code=0x73=115 (KEY_VOLUMEUP)
└──┴─ type=0x0001 (EV_KEY)
```

> **方法论四：认设备要认 Name，不要认"谁在动"。** `/dev/input/event2` 是评估板残留的电阻触摸驱动在空抖、不停吐乱码——一个假设备恰好在动，会让你以为找对了。

## 4.5 踩坑档案

| 症状 | 真因 | 解法 |
|---|---|---|
| LED 不亮 | 内核开关没开（依赖链） | 开 6 个 |
| LED 亮但按键没反应 | 漏 `KEYBOARD_GPIO` | 补开 |
| `grep kelpbar` 零输出 | 设备名是驱动名 `gpio-keys` | 搜 `gpio` |
| event2 吐乱码 | 电阻触摸残留在空抖 | 认 Name 不认"谁在动" |
| 极性和预期反 | 硬件事实与推测不符 | 翻转 `GPIO_ACTIVE_*` 重烧（正常调试流程） |

# 第 5 章 · 触摸：I2C 外设的完整范式

> **目标**：手按屏幕，系统打印触摸坐标。
> **详细版**：[03-touch/README.md](../03-touch/README.md)
> **本关是 I2C 外设调试的完整教科书**：以后遇到任何 I2C 芯片（传感器、RTC、音频……），流程一模一样。

## 5.1 硬件事实（三重实证）

| 项目 | 值 | 证据 |
|---|---|---|
| 触摸芯片 | GT9xx（电容触摸） | 内核 probe 日志 `gt9xxnew_ts 1-005d` |
| I2C 总线 | **TWI1**（不是评估板的 twi2！） | 原理图第 7 页 FPC 座走线 |
| I2C 地址 | 0x5D | 上板应答实测 |
| 数据脚 | SCL=PE0 / SDA=PE1 | 原理图 + 内核 C 表（PE0/PE1 的 function 4 = twi1） |
| 中断/复位 | INT=PE5 / RST=PE4 | 原理图 |

原理图 PE 端口区——TP_INT/TP_RST/TP_SCL/TP_SDA 四根线从 PE5/PE4/PE0/PE1 引出（PE12/PE13 打叉=未使用）：

![触摸 PE 区原理图](images/sch_p1_pe_zone.png)

### ★ 本关三条认知金句（I2C 调试的精华）

| 金句 | 含义 | 对应的坑 |
|---|---|---|
| **枚举 ≠ 应答** | 设备树里声明了 i2c 客户端，`/sys` 里节点就"存在"；但芯片是否真的应答，要靠 probe 实际通信 | 曾看到 `2-0014` 节点存在以为找到了芯片，其实它从未应答 |
| **控制器对 ≠ 线对** | 总线号开对了 ≠ 引脚对了 | TWI1 开了，但引脚配在板级默认 PE14/PE15，实际线在 PE0/PE1 → 满屏 NACK |
| **能力 ≠ 接线** | 芯片某脚"支持"某功能 ≠ 板子就接在那 | 内核 C 表说 PE14/PE15 也能做 TWI1（芯片能力），但原理图上根本没接（实际接线） |

## 5.2 三次手术（诊断实录）

> ### ★ 先说清刀口在哪：三次手术全部改**同一个文件** —— `board.dts`（设备树）
>
> 路径：`~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/board.dts`（改真身，第 3 章软链接陷阱）。
>
> **为什么触摸的问题全在设备树？** 触摸驱动（gt9xx）内核自带，**驱动代码一行不用改**；
> 它需要内核告诉它三件事：挂哪条 I2C 总线（TWI1）、芯片地址（0x5D）、中断/复位脚（PE5/PE4）。
> "这块板的硬件长什么样"这类信息，Linux 的规矩就是写进设备树——**驱动通用，板间差异全落在 dts**。
> 查依据用的"字典"还是内核 C 表 `pinctrl-sun8iw20.c`（第 3 章那套 `PINCTRL_PIN(E, 0)` 搜法）。
>
> | 手术 | board.dts 里改哪一段 | 为什么要改这里 |
> |---|---|---|
> | ① 删幽灵节点 | **`twi0` 总线下的旧 `ctp@14` 整段删掉** | 驱动用"全树第一个叫 ctp 的节点"找人，旧节点排前面会挡道（诊断见下） |
> | ② 改引脚 | **`twi1_pins_a`/`twi1_pins_b` 的 `pins = "PE14","PE15"` → `"PE0","PE1"`** | 板级默认抄的评估板引脚，本板实际接线在 PE0/PE1（原理图 + C 表双证） |
> | ③ 关 twi2 | **`twi2` 的 `status = "okay"` → `"disabled"`** | 本板触摸不在 twi2；且 twi2 与 usb_id_gpio 抢 PE12 脚 |

**手术一：幽灵节点遮蔽。** 日志报 `ctp is not used`。读驱动源码（`drivers/input/init-input.c`）：它用 `of_find_node_by_name(NULL, "ctp")` 找节点——**返回整棵树里第一个叫 ctp 的节点**（忽略 @ 后缀）。twi0（disabled）下藏着一个旧 `ctp@14` 排在前面，把正确的挡住了。修：删幽灵节点，保证全树只剩一个 `ctp@`。
（附带教训：驱动里那句 `please put sys_config.fex ctp_used set to 1` 是**过时提示语**，会把你带偏去改 fex——**别信打印，去读源码**。）

**手术二：引脚配错。** 日志满屏 `ACK not received / GTP i2c test failed`——总线通了、没人应答，波形发在空脚上。修：`twi1_pins_a/b` 的 `pins = "PE14","PE15"` → `"PE0","PE1"`。

**手术三：引脚冲突。** `pin PE12 already requested`——twi2 和 usb_id_gpio 抢脚。修：twi2 设回 `disabled`（本来就该关，一石二鸟）。

## 5.3 最终正确配置

```dts
&twi1 {
	clock-frequency = <400000>;
	pinctrl-0 = <&twi1_pins_a>;
	pinctrl-1 = <&twi1_pins_b>;
	status = "okay";

	ctp@5d {
		compatible = "allwinner,goodix";
		reg = <0x5d>;                    /* I2C 地址 */
		ctp_twi_id = <0x1>;              /* 1 = TWI1 */
		ctp_twi_addr = <0x5d>;
		ctp_screen_max_x = <0x2D0>;      /* 720 */
		ctp_screen_max_y = <0x2D0>;      /* 720 */
		ctp_int_port = <&pio PE 5 GPIO_ACTIVE_HIGH>;
		ctp_wakeup   = <&pio PE 4 GPIO_ACTIVE_HIGH>;
		status = "okay";
	};
};

twi1_pins_a: twi1@0 {
	pins = "PE0", "PE1";                 /* 原板级默认是 PE14/PE15，已改 */
	function = "twi1";
};
```

## 5.4 验证：从 probe 到坐标

| 关 | 命令 | 期望 |
|---|---|---|
| 1 芯片通信 | 串口日志 | `probe success`，无 NACK |
| 2 驱动注册 | `cat /proc/bus/input/devices` | `Name="gt9xxnew_ts"`，`Handlers=... event5` |


# 第 6 章 · 显示：六层挖根抓住真凶

> **目标**：屏幕点亮出画面（八色彩条），复位后自动恢复。
> **详细版**：[04-display/doc/显示-从黑屏到彩条全程教程.md](../04-display/doc/显示-从黑屏到彩条全程教程.md)（1140 行保姆级）
> **本关价值**：展示了"黑屏"这种最吓人的问题怎么**一层层剥**到真凶，全程推理链无一步跳跃。

## 6.1 硬件事实

| 项目 | 值 |
|---|---|
| 面板 | FL7707N，**MIPI DSI 4 lane** |
| 分辨率 | **720×1424** |
| 背光 | PWM 调光 |

## 6.2 六层挖根（黑屏推理链）

黑屏 = 屏幕不亮。按下面顺序逐层排除，**每一层都有日志证据**：

```
① 串口日志里没有 lcd_open_flow 系列 → 内核根本没初始化屏幕
② 日志里有 smooth display screen → U-Boot 抢先开了屏，内核"礼让"跳过初始化
③ 改 lcd_used=0 无效 → ★ 它不是开关！lcd_used 只用于分辨率合法性校验（名字骗人）
④ 追 U-Boot 源码 → 真开关是编译宏 CONFIG_BOOT_GUI：它无条件开屏
⑤ 关掉宏重编，镜像小了 32KB → 物证：GUI 代码真的被裁掉了
⑥ fb 变成 1024×600 ≠ 面板 720×1424 → 再改 fb0_width/fb0_height
```

> **方法论五：名字骗人，去看谁用它。** `lcd_used` 听起来就是"用不用 LCD"的开关，实际不是。
> 判断一个配置项是不是开关，**去读解析它的代码**，不猜。

**金句：谁开屏就改谁。** 屏幕被 U-Boot 开的，改内核参数没用——这决定了排查方向。

### ★ 这一关的改动落点（改哪两个文件、为什么）

| 改什么 | 完整路径 | 为什么是它 |
|---|---|---|
| 关 `CONFIG_BOOT_GUI` | `~/T113-Tina5.0-V1.2/brandy/brandy-2.0/u-boot-2018/configs/sun8iw20p1_auto_defconfig`（同目录 `.config` 一起改） | 开屏动作是 **U-Boot** 干的，这个开关是 **U-Boot 的编译宏**——必须改 U-Boot 源码树里的配置，改内核侧没用（对应"谁开屏就改谁"） |
| `fb0_width/fb0_height` → 720/1424 | `~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/board.dts` 的 `disp@5000000` 节点 | framebuffer 的逻辑尺寸必须等于面板物理尺寸，显示参数归设备树的显示节点管 |

> U-Boot 和内核都动了 → 这次必须**全量重编 + 重烧**（不像只改 env.cfg 时可以只 pack）。

## 6.3 彩条持久化（一个内核内存变量的落盘问题）

彩条（colorbar）命令改的是**内核内存变量**，重启清零。持久化方案：

```sh
# 手动开彩条（先确认屏能出画面）
```

# 第 7 章 · 喇叭：一条极性坑毁两天

> **目标**：板子播放音乐出声。
> **详细版**：[05-speaker/doc/喇叭-播放音频全程教程.md](../05-speaker/doc/喇叭-播放音频全程教程.md)

## 7.1 音频输出链路（先看清全链，坏哪查哪）

```
音乐文件 → 播放器(aplay/madplay) → ALSA → 内置 audiocodec(DAC) → HPOUT
        → LM4871 功放 → CN2 喇叭座 → 喇叭
```

| 部件 | 事实 | 证据 |
|---|---|---|
| 声卡 | `audiocodec`（T113 内置，card 0） | `/proc/asound/cards` |
| 功放 | LM4871（3W 类 AB） | 原理图第 5 页（下图） |
| 功放使能脚 | **PA_SHDN 接 PB2**（全局 gpio 34 = 1×32+2） | 原理图第 1 页引脚 86 |
| 喇叭座 | CN2（HC-1.25-2PWT） | 原理图第 5 页 |

## 7.2 ★ 本关核心坑：SHDN 极性（两天无声的真相）

原理图 AUDIO 页——注意 **SHUTDOWN 脚（1 脚）走 PA_SHDN 网络，经 R138 100kΩ 下拉到 GND**：

![LM4871 功放原理图](images/sch_speaker_zoom.png)

查 TI LM4871 数据手册：**SHUTDOWN 脚加高电平 = 进入关断模式**。
所以：

- **低电平 = 工作**（板上 100kΩ 下拉让默认状态就是工作）
- **把 PB2 拉高 = 把功放关掉**（当时以为"使能脚当然拉高"，拉了两天无声）

> **方法论六：SHDN 类引脚的极性必须查数据手册。** "使能脚拉高"是直觉，不是事实——带 SHDN/EN 字样的脚，极性各家不一样，**一张 datasheet 截图胜过两天瞎试**。

### ★ 改哪里：本关不改任何驱动

声卡驱动固件自带，功放芯片也不需要驱动（使能脚就是一根普通 GPIO）——本关**全部改动是运行时配置**：

| 改什么 | 在哪改 | 为什么 |
|---|---|---|
| 功放使能 | sysfs 直接操作 `/sys/class/gpio/gpio34/value`（拉低） | 使能脚 PA_SHDN 接 PB2=gpio34，GPIO 接口即可控制，不用碰内核 |
| 音量/通路开关 | `amixer` 命令（ALSA 混音器接口） | 标准音频控制接口， audiocodec 驱动已暴露这些控件 |
| **开机自动生效** | 板上 `/etc/rc.local` + SDK 源 `openwrt/target/t113/t113-evb1_auto_nand/base-files/etc/rc.local` | 只改板上重烧会丢（第 2 章落盘三定律），两处都写才稳 |

## 7.3 三条核心命令

```sh
# ① 功放使能（★ 低电平=工作）
MSYS_NO_PATHCONV=1 adb shell "echo 34 > /sys/class/gpio/export; echo out > /sys/class/gpio/gpio34/direction; echo 0 > /sys/class/gpio/gpio34/value"

# ② 音量链（HPOUT 开关 + 增益 + DAC 音量）
MSYS_NO_PATHCONV=1 adb shell "amixer cset name='HPOUT Switch' 1; amixer cset name='HPOUT Gain' 7; amixer cset name='DACL Volume' 200; amixer cset name='DACR Volume' 200"

# ③ 播放（WAV 用 aplay；MP3 需固件含 madplay）
MSYS_NO_PATHCONV=1 adb shell "aplay /root/audio/test_440.wav"
MSYS_NO_PATHCONV=1 adb shell "madplay /root/audio/music_twinkle.mp3"
```

> MP3 支持是 OpenWrt 包 `madplay` + `libid3tag`，选上重编即可（成品镜像 v8 比 v7 大 128KB = 它俩的体积，**镜像大小变化就是"真编进去了"的物证**）。
> 配置已固化进 SDK 的 `base-files/etc/rc.local`，烧录开机即生效。

## 7.4 没声音排查顺序（按这个查，别瞎试）

| 顺序 | 查什么 | 命令 | 期望 |
|---|---|---|---|
| 1 | 功放使能 | `cat /sys/class/gpio/gpio34/value` | **0**（1=被关断） |
| 2 | HPOUT 开关 | `amixer cget name='HPOUT Switch'` | on |
| 3 | 音量 | `amixer cget name='HPOUT Gain'` | 7 |

# 第 8 章 · 麦克风：录音 + 数据验证

> **目标**：对板载麦克风说话，录音，再从喇叭回放。
> **详细版**：[06-mic/README.md](../06-mic/README.md)
> **前置**：喇叭完成（回放靠喇叭），**关掉音乐循环**（声卡共用，会抢占）。

## 8.1 硬件事实

原理图 AUDIO 页的麦克风电路——GMI4015P 驻极体麦克风，R148（75Ω）从 AVCC 供电做**偏置**，信号经 C85/C86（100nF）耦合进 MIC_IN_3P/3N 差分输入：

![板载麦克风原理图](images/sch_mic_zoom.png)

- **驻极体麦克风（ECM）内部有 FET，必须外部偏置电阻供电**才能输出信号——这是它和 MEMS 麦克风的关键区别。
- 录音走 **MIC3 差分输入** → 内置 audiocodec 的 ADC3。混音器三件套（rc.local 出厂预设已生效）：`MIC3 Input Select=1` / `MIC3 Switch=on` / `ADC3 Gain=19`。
- **本关零配置改动**（为什么）：评估板和本板的麦克风都接在 MIC3 差分输入上，出厂预设正好匹配本板硬件——配置已在 `base-files/etc/rc.local` 里，开机自动生效，直接录就行。
- 录和放**共用一张声卡**（card 0），走不同子设备：playback=`pcm0p`，capture=`pcm0c`。

## 8.2 录音与回放

板上用标准 ALSA 工具（本固件**没有** tinyalsa 的 tinycap）：

```sh
# 录 5 秒（16kHz 单声道，人声够用——奈奎斯特：16kHz 采样可还原 8kHz 内信号）
MSYS_NO_PATHCONV=1 adb shell "arecord -f S16_LE -r 16000 -c 1 -d 5 /root/audio/test_rec.wav"
# （录音时对着板子上 MIC 丝印旁的金色圆麦说话）

# 回放
MSYS_NO_PATHCONV=1 adb shell "aplay /root/audio/test_rec.wav"
```

## 8.3 ★ 本关方法论：命令没报错 ≠ 功能正常

`arecord` 不报错**不代表录到了声音**——麦克风坏了它照样安静地"录"5 秒全零。**把数据拉回来分析**：

```python
import wave, struct, math
w = wave.open('test_rec.wav','rb')
n = w.getnframes()
samples = struct.unpack('<%dh' % n, w.readframes(n))
print('peak', max(abs(s) for s in samples))                 # 峰值
print('rms ', math.sqrt(sum(s*s for s in samples)/n))       # 平均能量
print('nz  ', sum(1 for s in samples if abs(s) > 100))      # 活跃采样数
```

| 指标 | 纯数字静音 | 真实录音 |
|---|---|---|
| peak | 0 | 数百 ~ 32767 |
| rms | 0 | 数百 |
| 活跃采样 | 0 | 大量 |

本项目实测 **peak=32767、rms=393** —— 模拟信号真实被数字化了，通路工作 ✓。

## 8.4 踩坑档案

| 症状 | 真因 | 解法 |
|---|---|---|
| `Device or resource busy` | **音乐循环还在跑**（while true 不停拉起 madplay 抢声卡） | 连循环 shell 一起杀，不只杀播放器 |
| 录的全是嗡嗡底噪 | 增益太高/环境吵 | 调 `ADC3 Gain`（0~31） |
| 回放声小 | 录音侧增益低 | `ADC3 Gain` 调 19~25 |
| `tinycap: not found` | 本固件用标准 ALSA | 用 `arecord` |

# 第 9 章 · WiFi：给板子换正确的驱动

> **目标**：连手机热点，ping 通公网。
> **详细版**：[07-wifi/README.md](../07-wifi/README.md)
> **本关性质特殊**：不是"调试"，而是**天生装错驱动**——换驱动的完整工程流程。

## 9.1 诊断三步（每步都有实锤）

```sh
# ① 芯片活着吗——SDIO 总线枚举
MSYS_NO_PATHCONV=1 adb shell "cat /sys/bus/sdio/devices/*/vendor; cat /sys/bus/sdio/devices/*/device"
# vendor=0x024c device=0xd723 → Realtek RTL8723DS（与原理图 U11 吻合）
```

**而开机日志是**：

```
[XRADIO] Detect SDIO card 0        ← 总线发现了芯片
[SBUS_ERR] sdio probe timeout!     ← XR829 驱动跟它"说话"，芯片听不懂
```

固件里装的是全志自家的 **XR829** 驱动，芯片却是 Realtek 的——品牌错配，协议完全不同。

```sh
# ② 确认固件里没有正确驱动
grep -iE 'RTL8723|XR829' ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/config-5.4      # 只有 XR829
```

③ 换驱动（三连跳的教训）：

| 尝试 | 结果 | 教训 |
|---|---|---|
| rtl8821cs 驱动（内核树里有 8723d 头文件） | ✗ `drv_types.h: No such file` | 裁剪版 + O= 构建下相对 include 失效 |
| rtl8723ds **内置 =y** | ✗ `multiple definition of aes_encrypt` | 自带加密库的驱动**必须编成模块 =m**（和内核 lib/crypto 符号撞车） |
| rtl8723ds **模块 =m** | ✓ SDK 原生集成源码，编译通过 | |

## 9.2 ★ 本关最大收获：KernelPackage 机制

**问题**：`.ko` 编出来了，但 rootfs 里没有——OpenWrt 的 rootfs **只装"被选中的包"**，裸 .ko 不自动进。

**解法**（三件套）：

1. **定义包**（`openwrt/openwrt/target/linux/t113-common/modules.mk`，照抄 net-xr829 的格式）：

```
define KernelPackage/net-8723ds
  SUBMENU:=$(WIRELESS_MENU)
  TITLE:=Realtek RTL8723DS SDIO WiFi support
  DEPENDS:= +@IPV6 +kmod-cfg80211
  KCONFIG:=CONFIG_RTL8723DS=m CONFIG_RFKILL=y CONFIG_RFKILL_GPIO=y
  FILES:=$(LINUX_DIR)/drivers/net/wireless/rtl8723ds/8723ds.ko
  AUTOLOAD:=$(call AutoProbe, 8723ds)
endef
$(eval $(call KernelPackage,net-8723ds))
```

2. **选包**（`openwrt/target/t113/t113-evb1_auto_nand/defconfig`）：`CONFIG_PACKAGE_kmod-net-8723ds=y`
3. 重编 → 以后每次 `build.sh` 自动把 8723ds.ko 装进 rootfs 并生成 `/etc/modules.d/net-8723ds` 开机自动加载。**一劳永逸，这才是工程做法。**

**连带坑**：驱动加载报 `get wifi_sdc_id failed` → dts 里 **rfkill@0 父节点 disabled，wlan@0 子节点被连坐**（设备树规则：父 disabled 则子不加载）。确认 rfkill 新配置只引出 PG11、不再抢串口引脚后，改 okay。

## 9.3 连热点（含中文 SSID 坑）

```sh
# 傻瓜命令（ASCII 名称时）
wifi -o sta && wifi -s && wifi -c <名称> <密码>

# 名称不对劲时，用 wpa_cli 看芯片实际广播的名字（★ 别信你设置的名字）
wpa_cli -p /etc/wifi/wpa_supplicant/sockets -iwlan0 scan; sleep 4
wpa_cli -p /etc/wifi/wpa_supplicant/sockets -iwlan0 scan_results
```

**实测坑**：热点叫"名称1"，连不上。hexdump 扫描结果发现手机实际广播的 SSID 只有 `31 0a`（"1\n"）——**中文字符被手机丢了，真名是 "1"**。按真实名字 set_network 后连上。

**验证三层**：

```sh
wpa_cli -p /etc/wifi/wpa_supplicant/sockets -iwlan0 status   # wpa_state=COMPLETED + ip_address=192.168.26.40
ping -c 3 223.5.5.5                                          # 3 包全通 ~60ms = 互联网真通
```

> 链路层（COMPLETED）→ 网络层（拿到 IP）→ 传输层（ping 通）三层验证，才算"WiFi 好了"。

# 第 10 章 · 蓝牙：串口回显 + 手机把板子当音箱

> **目标**：① 电脑通过蓝牙串口连板子双向收发（SPP 业务）；② 手机连板子放歌流畅（A2DP）。
> **详细版**：[08-bt/README.md](../08-bt/README.md)；**全部实际报错与排查过程**：[08-bt/doc/蓝牙问题排查全记录.md](../08-bt/doc/蓝牙问题排查全记录.md)
> **本关是全书最难的**：芯片适配 → 配对 → 业务 → 音频 → 带宽优化，五层问题叠在一起。这里讲主线，报错细节看排查全记录。

## 10.1 硬件背景：蓝牙走哪条线

RTL8723DS 是 WiFi+BT 二合一：**WiFi 半边走 SDIO**（第 9 章），**蓝牙半边走 UART1**（PG6/PG7，H5 协议 = 3-wire），固件由 `rtk_hciattach` 每次开机下载进芯片：

![蓝牙 UART1 走线](../08-bt/doc/images/bt_uart1_pg6-9.png)

> 注意 PG8/PG9（RTS/CTS）板上**没有引出连接**——这条事实在第 10.5 节会变成一个坑。

**关键机制**：芯片固件在 RAM 里，**每次断电都丢**，每次开机重新下载。所以改 config 文件改的是"下载行为"；也所以打断下载过程可能让芯片卡在半初始化状态（假死），**唯一解法是整机断电 15 秒**。

## 10.2 蓝牙芯片起不来：成功配方五条件

| # | 条件 | 缺了会怎样 |
|---|---|---|
| 1 | 芯片冷启动（断电 15 秒） | 假死芯片 attach 报 `IC: NONE`，软重启救不活 |
| 2 | 移除 `rtl8723d_config`（它指示 4.9M 波特+硬件流控，超出板子能力） | 固件下载超时 ×40 |
| 3 | `btmgmt ssp on` + `btmgmt io-cap 3` | 传统 PIN →"配对码不匹配" |
| 4 | `btmgmt bondable on` | "已拒绝配对" |
| 5 | `hciconfig hci0 class 0x240404`（音频类；class=0 会被手机/电脑隐藏） | 搜不到设备 |

以上全部固化在 `/etc/bt_up.sh`（开机自启，`/root` 双份互备）。

## 10.3 SPP：电脑 ↔ 板子双向串口（"配对 ≠ 连接"的业务验证）

**认知升级**：配对=交换密钥建立信任；**连接=跑具体业务**。手机显示"已配对"只说明第一步完成。业务要跑起来，板子得**注册服务**（SDP 记录）并**监听**：

```sh
bluetoothd -n -C                          # -C 兼容模式：创建 /var/run/sdp，否则 sdptool 连不上
sdptool add --channel=3 SP                # 注册串口服务记录（内存里，开机要重注册）
rfcomm -r listen /dev/rfcomm0 3 &         # -r 关 tty 回显（板上没有 stty）
# 业务脚本 spp_demo2.sh：等连接 → 发问候 → 收一行回一行（T113-Echo: xxx）
```

**电脑侧**：Windows 蓝牙设置配对 T113-KelpBar → 设备管理器出现两个 COM 口：`_LOCALMFG&0000` 是本机入口（别用），InstanceId 带板子地址 `347563484AAD` 的才是出口。串口工具打开出口 COM，即见问候语，双向回显通。

**本节最重要的机制**（后面 A2DP 还要用两次）：

> ★ **对端的 profile 列表 = 配对那一刻的 SDP 快照。** 板子事后补注册服务，电脑/手机**不会自动知道**，必须**删除配对重新配对**才刷新。固定顺序：**先修好板子服务，再让对端重配**。反过来 = 白配。

## 10.4 A2DP：手机连板放歌（五层坑，剥洋葱）

手机把板子当蓝牙音箱：`手机 --A2DP--> bluealsa --> audiocodec --> LM4871 --> 喇叭`。
每一层坑都由 btmon 抓包/btmgmt/bluetoothd 日志定位（详见排查全记录第三幕），这里只列洋葱层：

| 层 | 症状 | 真相 | 修法 |
|---|---|---|---|
| 1 | 手机只显示"已保存"连不上 | `Authentication attempt without agent`——没有配对 agent，鉴权无人应答 | bt_agent.sh 常驻（NoInputNoOutput + default-agent） |
| 2 | 手机报"PIN 码不正确" | 板子宣称 DisplayYesNo 却没人按确认，30 秒超时（报错误导）；bluetoothctl 启动会自动注册 KeyboardDisplay agent 抢角色 | `bluetoothctl --agent NoInputNoOutput` 启动参数 + 30 秒自愈夺回；排查只用 btmon/btmgmt |
| 3 | 双配对成功但连不上 | Audio Sink 端点/SDP 记录丢失（`sdptool browse local` 此板还不可靠，不能当依据） | 重启 bluealsa，看 bluetoothd 日志 `Endpoint registered` |
| 4 | 重配后没有「媒体音频」开关 | 配对快照机制（见 10.3★）——配对发生在服务丢失期间 | 先修服务再删配对重配 |
| 5 | 重配后**还是**没有开关 | btmon 实锤 SDP 应答 5 字节空（0 条记录）——BlueZ 5.54 + -C 的坑，A2DP SDP 记录不自动生成 | `sdptool add A2SNK` 手动补 + bt_up.sh 服务自检循环 |

**修完第 5 层后手机重配**：详情页出现「媒体音频」→ 打开 → **T113-KelpBar [SBC] 已连接 | 使用中（媒体）** ✓

三个"像坏了其实正常"：已配对设备不再出现在扫描列表；A2DP 空闲 ~31 秒自动断（放歌自动重连）；`/proc/asound/.../status` 显示 closed（只在真正播放时开流）。

## 10.5 A2DP 卡顿：带宽之战（定量分析的胜利）

**症状**：连上了、也出声了，但一卡一卡。

**先算账，不瞎试**：

```sh
# 实测到达速率：8 秒 RX 字节差值
hciconfig hci0    # 记 RX bytes → 等 8 秒 → 再记
# 81,538 B ÷ 8 s ≈ 10.2 KB/s
```

| 项 | 数值 |
|---|---|
| UART1 实测吞吐（115200） | **10.2 KB/s** |
| 立体声 SBC 需求 | **~41 KB/s** |

**管道只有需求的 1/4** —— 数据饿死，不是喇叭接触问题（接触不良是咔啦杂音，数据饿死是整段断流，现象性质不同）。内核 overrun/HCI 错误计数全 0，排除驱动层。

**死路（实测）**：改芯片波特率 1.5M——config 编码正确（日志实锤解析成功），但固件下载仍超时，且每次失败芯片假死必须断电，最终放弃回退 115200。（PG8/PG9 未接 → 流控位也是坑；sunxi UART 整数分频，921600 反而偏差 23%。）

**正路：从协商层压住手机码率。** 读 bluez-alsa 源码发现 `--a2dp-force-mono` 只改 **source** 端（板子作音源），**sink** 端（板子作音箱，我们的场景）能力声明原封不动——手机照样选立体声。修改 `src/a2dp.c`：

```c
static struct a2dp_codec a2dp_codec_sink_sbc;              /* 去掉 const */
a2dp_codec_sink_sbc.capabilities.sbc.channel_mode = SBC_CHANNEL_MODE_MONO;
a2dp_codec_sink_sbc.capabilities.sbc.max_bitpool = 10;     /* 先 12 后 10 */
```

**为什么是 10（算账）**：bitpool 12 单声道净载荷 ~7.5KB/s + 协议开销 ~2.7KB/s ≈ 10.2KB/s = 恰好顶满（零星小卡）；**bitpool 10 ≈ 8KB/s，留 20% 余量 → 流畅**。A2DP 规范要求手机在 sink 广播的能力范围内选择——sink 收窄，手机只能低码率编码，从源头根治。

**交叉编译四件套**（VM）：

```bash
export PATH=~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/toolchain/bin:$PATH
export STAGING_DIR=~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/target   # wrapper 强制要求
ln -sf arm-openwrt-linux-gnueabi-gcc-8.3.0 \n  ~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/toolchain/bin/arm-openwrt-linux-gcc  # 补短名软链
cd ~/T113-Tina5.0-V1.2/out/t113/evb1_auto_nand/openwrt/build_dir/target/bluez-alsa-20211122 && make -C src
# 产物 src/bluealsa → 取回 Windows → adb push /usr/bin/bluealsa → start-stop-daemon 重启
```

**验证只认协商层**（方法论七）：

> **验证边界原则**：协议协商（btmon 里 AVDTP Set Configuration 的 `Maximum Bitpool`）= 唯一可信判据。
> ALSA `hw_params` 显示 channels:2 **不作数**（aplay 恒开双声道，单声道流被复制）；RX 速率顶格**不作数**（两种配置都顶满）；体感"好多了"**不作数**（可能是缓存协商的错觉）。
> 另外：改 sink 能力后，手机**关开媒体音频开关不足以**重读能力（安卓按设备缓存协商结果），要**重启手机蓝牙开关**才重新 GET_CAPABILITIES。

btmon 实锤 `Maximum Bitpool` 协商成功 + bitpool 10 版本播放流畅 → **2026-10-14 用户验收收工**。
