# 机器人方向面试考题答案（三）

> **用法**：先自己口头作答，再对照。A 组给的是**答题思路和示范要点**（面试答项目没有标准句，有标准结构）；其余组给标准答案要点。标"💡"的是加分句。

## A 组 · 项目实战题

**1. 介绍一下你的项目（30 秒版 + 2 分钟版）**
- 30 秒：背知识讲解 5.1 的电梯陈述——"全志 T113 板级适配全流程：串口→GPIO→I2C 触摸→MIPI 屏→音频→WiFi→蓝牙→LVGL 图形，涉及 U-Boot、内核、设备树、交叉编译，全程靠日志和抓包定位，有完整问题档案。"
- 2 分钟版结构：背景（非参考设计板，官方配置配评估板）→ 流程（地基串口→外设逐个→无线→图形）→ 方法（证据定位，不瞎试）→ 结果（8 项全通+15 个问题档案）。

**2. 板子和评估板的区别？移植的本质？**
- 区别：调试串口脚不同（评估板 PG8/PG9 vs 本板 PB6/PB7）、触摸挂的总线不同（评估板 twi2 vs 本板 TWI1）、WiFi 芯片品牌不同（评估板 XR829 vs 本板 Realtek）。
- 移植的本质：**让软件配置匹配实际硬件**。举例：官方配置说串口在 PG8，本板焊在 PB6——不改配置，开机日志发到没人听的脚上。同源码、不同配置，这就是 BSP 的意义。

**3. 启动流程 + 项目里碰到的问题**
- 流程四步：BootROM → 引导程序（U-Boot）→ 内核 → init/根文件系统。
- 项目问题：调试串口在引导期和内核期各读各的配置（fex 和设备树），只改一处日志就断一段；还遇到过内核精确卡死，用 initcall 调试定位到空总线死等。

**4. 为什么改三处？**
- 早期打印（内核刚解压驱动没加载）要**寄存器地址**；U-Boot 阶段读 fex；内核阶段读设备树——三个阶段各读各的配置，少改一处日志就从那里断。

**5. 设备树 + 实际例子**
- 是什么：描述硬件的文本，编译后交给内核，让它知道"什么硬件在哪、什么参数"。需要它的原因：同一份内核跑不同板，板间差异全在设备树，不用改内核代码。
- 例子（任选一）：①触摸节点被旧节点挡道——内核找"全树第一个匹配名的节点"，删幽灵节点；②I2C 引脚从板级默认改成本板实际接线，引脚编号查内核 pinctrl 表确认；③fb 尺寸改成面板尺寸。

**6. 内核卡死怎么排查？**
- 方法论：先区分"确定性卡死"（每次停同一行=软件问题）和随机复位（=硬件/看门狗）。打开内核的 initcall 调试开关，每个驱动初始化前后都打印——**凶手就是只有"calling"没有"returned"的最后一个驱动**。再搜返回码定位：-517 是"内核补考机制"（依赖没就绪先挂起重试），顺着它找到空总线死等。修法：关掉空总线，带行号精准改（防止误伤启动必需的节点）。

**7. 怎么验证"真的在工作"？**
- 原则：**命令没报错 ≠ 功能正常**，要看数据。两个例子：①录音——arecord 不报错不代表录到声音，把文件拉回来算峰值和均方根（全零=没录到，实测峰值 32767、均方根 393）；②显示——先查分辨率接口返回的数字（720/1424）再肉眼看，数字对屏不亮=硬件侧，数字不对=软件侧。

**8. 最难的问题（讲故事二：带宽算账）**
- 结构：现象（放歌卡顿）→ 定量分析（实测管道 10.2 KB/s vs 需求 41 KB/s，四分之一）→ 两条路线（提速失败：芯片假死断电 15 秒才救活；降流量成功：改协商程序源码让板子只广播低码率能力，手机按规范只能选低的，流量压到 8 KB/s 留 20% 余量）→ 收获：**定量分析先于动手**。备选故事：配对快照机制（五层洋葱，抓包实锤）。

## B 组 · Linux 系统基础

**9. 进程 vs 线程**：进程=资源分配单位（独立地址空间），线程=调度单位（共享进程地址空间）。进程隔离好、开销大；线程通信免费（共享内存）但一个崩全崩。机器人：节点=进程（隔离、好定位），节点内回调=线程。

**10. 线程切换开销小**：进程切换要换页表（地址空间映射整个换掉）、TLB 失效、CPU 缓存变冷；线程同进程内切换只换寄存器和栈指针，缓存还热着。

**11. 两线程读写全局变量**：竞态条件——结果取决于执行顺序，且写入的**可见性**无保证（B 可能读到旧值 0，不只是"谁先谁后"的问题）。解决：互斥锁保护临界区，或改用原子操作。💡加分：volatile 只禁止编译器优化重排，**不保证原子性和可见性，不能替代锁**。

**12. 互斥锁 vs 自旋锁**：拿不到锁时，互斥锁**睡眠让出 CPU**（上下文切换有开销），自旋锁**原地忙等**。结论：临界区短/中断上下文→自旋锁；临界区长/进程上下文→互斥锁。内核里同理（mutex 可睡眠，spinlock 不可）。

**13. 死锁**：两组及以上执行流互相持有对方要的锁，卡死。四条件：互斥、占有且等待、不可剥夺、循环等待。避免：**统一加锁顺序**（最实用）、加锁超时、一次拿全。

**14. 原子操作**：不可被分割的读改写（计数器加减、标志位置位）。用在不需要锁的简单场景——无锁、无睡眠、最快。底层靠 CPU 特殊指令（如比较交换）实现。

**15. 用户态/内核态**：CPU 两级权限。用户态应用不能直接碰硬件和他人内存；分级的目的是隔离保护（应用崩不死系统、资源由内核统一仲裁）。

**16. 系统调用**：用户态主动陷入内核态请求服务的入口。例子（项目实战）：`echo 255 > /sys/class/leds/.../brightness` 这条命令背后是 write 系统调用 → VFS → LED 驱动 → 拉高 GPIO——一整条链路我都走过。

**17. IPC 方式**：管道（字节流，简单）、消息队列（格式化消息）、**共享内存（最快，零拷贝）**、socket（可跨机）、信号（异步通知）。选择：大数据量高频→共享内存+锁；跨机器→socket；简单通知→信号。

**18. 共享内存为什么配信号量**：共享内存只解决"数据放哪"，不解决"什么时候能读/写"——没有同步，读到写到一半的数据（脏数据）。信号量/锁负责节奏。💡加分：ROS2 同机节点间的 DDS 通信底层就是共享内存+锁的工业化封装。

**19. /proc /sys /dev**：/dev 是设备节点（open 后 read/write 操作硬件）；/proc 是进程和内核状态的投影；/sys 是设备和驱动的投影。三者都是内核生成的虚拟文件，不在磁盘。项目实例：event5（输入）、fb0（显存）、ttyS1（串口）；echo 写 /sys/class/gpio 拉功放脚。

**20. VFS 与一切皆文件**：虚拟文件系统是内核的抽象层——给上层统一的一套文件操作接口（open/read/write），下层可以是磁盘文件系统、设备、管道、网络。价值：同一套 API 操作一切（你 cat 一个设备和 cat 一个普通文件命令一样）。

**21. TCP vs UDP**：TCP 可靠有序（握手、重传、序号），有连接，延迟高一些；UDP 无连接不保证，快。机器人：远控/日志用 TCP；高频传感器流、ROS2 DDS 默认用 **UDP**（新的一帧比重传旧的更有价值）。

**22. fork 返回两次**：fork 一次调用，返回两次——父进程里返回子进程 PID，子进程里返回 0。相同：代码段、打开的文件；不同：PID、独立的地址空间（写时复制——先共享物理页，谁写谁复制，省内存又快）。

**23. 僵尸进程**：子进程退出后，父进程没"收尸"（没调用 wait 获取退出状态），子进程的进程表项残留。危害：占进程号。避免：父进程 wait/waitpid；或父进程先退出让 init 收养（init 负责收尸）。

## C 组 · 设备树与驱动

**24. compatible 的作用**：设备树节点与驱动的"接头暗号"。内核遍历设备树节点，拿 compatible 字符串去和各驱动源码里注册的匹配表（of_match_table）对照，**一字不差**就调用那个驱动的 probe。价值：驱动可以匹配多个 compatible（兼容多代硬件），节点写错一个字母就是"孤儿节点"（我有实战：写错/被挡道都会导致设备无声无息）。

**25. probe 何时调用、做什么**：设备和驱动匹配成功时被调用（设备树展开时、或驱动后注册时都会触发匹配）。里面做：取设备树资源（引脚、地址、中断号）→ 初始化硬件 → 注册到子系统（如输入子系统）→ 使能功能。probe 失败节点就等于不存在。

**26. 字符/块/网络设备**：字符设备按字节流顺序访问（串口、输入、显存）；块设备按块随机访问（NAND/eMMC/SD 卡）；网络设备走 netdev 接口，不走 /dev（用 socket 访问）。项目里我调的全是字符设备。

**27. read 一个 /dev 设备的完整链路**：应用调 read（库函数）→ **系统调用**陷入内核态 → VFS 找到该设备节点对应的结构 → 根据**设备号**找到**驱动** → 调用驱动 file_operations 里挂的 read 实现 → 驱动读硬件（可能 sleep 等数据）→ 数据拷回用户态缓冲 → 返回。💡加分：能报出 file_operations 这个结构名。

**28. 主/次设备号**：主设备号找**驱动**（哪套 file_operations），次设备号区分**同驱动的不同设备实例**（如 ttyS0/ttyS1 共用串口驱动）。

**29. 中断里为什么不能睡眠**：中断上下文**不属于任何进程**——睡眠意味着"挂起当前进程等唤醒"，但中断打断的可能就是别的进程，没有"当前进程"可挂；而且中断要尽快返回。睡眠会把这个 CPU 卡死。

**30. 中断下半部**：上半部（中断处理函数）只做紧急的（应答硬件、记时间戳），耗时工作推迟给下半部。三种：软中断（静态、最快、网络用）、tasklet（基于软中断、同类不并发、**不能睡眠**）、工作队列（**进程上下文、能睡眠**，适合可能睡眠的操作如 I2C 读）。经典题答案：**工作队列能睡，上半部和 tasklet 不能**。项目案例：触摸中断里只标记，读 I2C 坐标的慢活放下半部。

**31. 平台总线**：SoC 内部外设没有真实总线（不像 USB 能枚举），内核造了虚拟的 platform 总线：设备（设备树节点展开）和驱动各自注册，按 compatible 匹配后 probe。LED、串口控制器、I2C 控制器都走它。

**32. 输入子系统**：内核把所有输入设备（触摸/按键/鼠标）统一成一个框架——驱动只管"把事件报给子系统"，子系统统一变成 /dev/input/eventX 的事件流给应用。事件 16 字节：type（按键/坐标/同步）+ code（哪个键/X轴）+ value（按下/坐标值）。我 hexdump 过触摸坐标和按键事件。

**33. pinctrl**：管理引脚复用和电气属性的框架——一根脚同一时刻只能是一种功能（GPIO/串口/I2C...），由 pinctrl 统一仲裁。所以配置串口时功能号写错（或别的驱动抢了脚），就会"波形发到空脚"或"pin already requested"——我踩过 twi2 和 USB 抢 PE12 的案例。

## D 组 · 实时性

**34. 软/硬实时**：硬实时=超时就是事故，必须保证最坏响应时间（电机控制环错过 1ms 周期→抖动）；软实时=偶尔超时可接受（视频掉一帧、语音缓冲）。机器人里：控制环硬实时，感知规划软实时。

**35. 标准 Linux 为什么不是硬实时**：设计目标是**吞吐和公平**（CFS 调度器），不承诺最坏延迟；内核里大量不可抢占区（中断关闭段、自旋锁区）+ 中断响应不确定，最坏延迟可达几十毫秒且无上界保证。

**36. PREEMPT_RT 原理**：把内核改造成"几乎处处可抢占"——中断处理线程化（中断可被高优先级任务抢占）、自旋锁换成可抢占的实时锁、细化抢占点。**不提升平均性能，而是把最坏延迟压到几十微秒且稳定可预测**。现状：实时抢占已并入主线内核（6.12 起），Ubuntu 提供实时内核包。

**37. 优先级反转**：低优先级持锁 → 高优先级等锁 → 中优先级插队霸占 CPU → 高的被低拖死。解法：**优先级继承**（持锁的低任务临时提升到等锁的最高优先级，尽快放锁）。名场面：1997 火星探路者号在火星反复重启就是这个没处理好——地面上传补丁修复。

**38. 哪些任务实时**：跑实时优先级=电机/关节控制环（固定周期、超时=抖动）、安全停机逻辑；跑普通优先级=感知、规划、UI、日志。口诀：**感知可以丢一帧，控制不能迟一拍**。

**39. CAN 为什么常用**：多主差分总线、抗干扰强、带**优先级仲裁**（ID 小的先发，不会撞死）、硬件错误处理完善；带宽低（1 Mbps）但对控制指令够用。汽车和机器人电机统一走它（上位 Linux 通过 CAN 接口卡下发指令）。

## E 组 · ROS2

**40. ROS1 vs ROS2 核心区别**：①架构：ROS1 中心化（必须跑 Master，单点故障）→ ROS2 去中心化（DDS 自动发现，无中心节点）；②通信：自定义协议 → 标准 DDS（带实时 QoS）；③平台：仅 Linux → 跨平台+可跑嵌入式微控制器；④ROS1 已停止维护，新项目全部 ROS2。💡加分：没有 Master 意味着机器人断网重启后节点自己能恢复，鲁棒性质变。

**41. 三种通信 + 场景**：Topic 发布/订阅、单向流式、多对多（相机图像流、点云、速度指令）；Service 请求响应一问一答（查电量、设置参数）；Action 长时任务带过程反馈可取消（导航去 A 点途中持续上报位置）。口诀：**数据流用话题，问答用服务，干长活带进度条用动作**。

**42. 底层通信与发现**：底层是 **DDS**（数据分发服务，工业级中间件，常见实现 Fast DDS / CycloneDDS，可换）。发现机制：节点上线后通过 **UDP 组播**向同网段宣告自己、监听别人——去中心化，谁也不用当 Master。

**43. QoS 策略**：Reliability（Reliable 可靠重传 / BestEffort 尽力而为）、History+Depth（队列深度，满了一般丢最老）、Durability（晚加入的订阅者能否收到历史消息）、Deadline（超时检测）。例子：导航目标用 Reliable（丢不得），雷达点云用 BestEffort（丢帧没事，重传旧的没意义）。

**44. BestEffort 发布 + Reliable 订阅**：**收不到**。QoS 兼容规则是"订阅端的要求必须 ≤ 发布端能提供的"——订阅端要可靠、发布端给不了，DDS 直接不建立连接，且不一定报错（静默丢）。这是 ROS2 调试高频坑。

**45. 收不到消息的排查**：①`ros2 topic list` 两边都能看到对方吗 → ②检查 **ROS_DOMAIN_ID** 是否一致 → ③`ros2 topic info /xxx --verbose` 对比**两端 QoS** 是否兼容 → ④检查网络（组播被交换机/防火墙挡？跨网段？VPN？）→ ⑤时间是否同步。顺序体现了"先协议层、再网络层"的定位思路。

**46. ROS_DOMAIN_ID**：逻辑隔离域号（0-232），只有同域的节点互相可见。用途：同一网络多台机器人互不干扰（各占一个域）；同一台机隔离测试环境。默认 0。

**47. launch**：Python 写的启动编排脚本——一次拉起多个节点、配参数、重映射话题、设命名空间，还能按事件响应。价值：机器人十几个节点不可能手敲终端一个个起；launch 是系统的"开机自启+装配图"。

**48. tf/坐标变换树**：机器人身上一堆坐标系（base 基座、各关节、雷达、相机），tf 用**树**维护它们之间的平移旋转关系，任何时刻可查询任意两框的变换。为什么必须：雷达看到障碍物在"雷达系"坐标，要转到"机身系"才知道往哪躲——坐标系不统一，感知和规划对不上话。调试日常：`tf 树断了`（某帧没发布）= 下游全部查不到变换。

**49. Action 三段结构**：Goal（目标）→ Feedback（持续反馈进度）→ Result（最终结果），且支持**取消**。相比 Service：Service 是一问一答的阻塞调用，干长活时既没有进度、也不能取消、还占着调用线程。导航是典型——走了十分钟，中途要能改目的地。

**50. DDS 实现**：ROS2 把通信抽象成接口层（RMW），官方支持 Fast DDS（默认）、CycloneDDS、RTI Connext（商业）。可换：设置环境变量选实现——不同实现的性能和组网行为有差异，工程上遇到组网问题时换 DDS 实现是真实手段之一。

**51. 典型软件骨架**：传感器驱动（雷达/相机/IMU）→ 感知（定位 SLAM/障碍识别）→ 规划（全局路径+局部避障）→ 控制（运动学解算→速度指令）→ 硬件抽象层（电机驱动，CAN/串口下发）。横向贯穿：tf 坐标树、参数系统、rosbag 录制、launch 编排。面试讲系统设计按这条数据流从上往下走。

## 答题心法（最后三条）

1. **项目题永远往方法论上收**：面试官问细节不是考记忆，是看你怎么思考——每个故事结尾都落在"我是怎么定位的"（证据→假设→验证）。
2. **不会的题诚实+展示迁移**："ROS2 我还在学，但它底层 DDS 就是 IPC+网络，我 Linux 底层的底子能直接迁移"——比不懂装懂强十倍。
3. **背这三组数字当锚点**：带宽账 10.2/41 KB/s；最坏延迟几十毫秒→几十微秒（PREEMPT_RT）；QoS 规则"订阅端要求 ≤ 发布端提供"。有数字的人显得真做过。
