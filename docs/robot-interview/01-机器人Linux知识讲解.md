# 第 1 部分 · Linux 系统基础（机器人岗必考的地基）

## 1.1 Linux 启动流程（你亲手做过的那四步）

**面试标准答案**（用你 T113 的经历讲，比背书强十倍）：

```
上电 → BootROM（芯片内置，初始化最基础硬件，加载下一级）
     → 引导程序（U-Boot：初始化内存/存储/串口，把内核从存储读进内存，启动时把设备树地址传给内核）
     → Linux 内核（挂载根文件系统，启动第一个用户态进程）
     → init 系统（现代发行版用 systemd，按依赖关系拉起各种服务）
     → 登录/应用
```

- **你做过的事**：把调试串口从评估板的脚移植到本板的脚——改了 U-Boot 阶段配置、内核设备树、早期控制台参数三处，因为**三个阶段各读各的配置**。面试官听到这句就知道你真做过。
- **延伸考点**：systemd 和 SysV init 的区别（并行启动 vs 串行脚本）；内核启动后第一个进程是谁（PID 1，死了系统就崩）。

## 1.2 进程与线程（每场面试必考第一题）

| 维度 | 进程 | 线程 |
|---|---|---|
| 本质 | 资源分配的**基本单位** | CPU 调度的**基本单位** |
| 地址空间 | 独立（互相看不见内存） | **共享**所属进程的地址空间 |
| 切换开销 | 大（要换页表、刷缓存） | 小（只换寄存器和栈） |
| 崩溃影响 | 一个进程崩不影响别的 | 一个线程崩，**整个进程**死 |
| 通信方式 | 需要 IPC（管道/共享内存/socket…） | 直接读写共享变量（但要同步！） |

- 创建：进程 `fork()`（写时复制，父子先共享物理页，谁写谁复制）；线程 `pthread_create`（同进程内，共享堆、全局区，各自有栈）
- **机器人场景**：ROS2 里每个节点通常是独立**进程**（崩了不连坐，好定位）；一个节点内部用**线程**跑回调。
- 调度：Linux 用 CFS（完全公平调度器）管普通进程（按虚拟运行时间加权）；实时调度两种策略：FIFO 和 RR（轮转），优先级 1-99 高于所有普通进程。

## 1.3 同步与互斥（第二必考，常出场景题）

**竞态条件**：多个执行流同时读写共享数据，结果取决于执行顺序——Bug。经典题：两个线程通过全局变量交换数据，A 写 100、B 读打印，B 有时打印 0——因为**写入的可见性和顺序没有保证**，需要同步机制（volatile 不解决这个，它只禁编译器优化）。

| 工具 | 用法 | 特点 |
|---|---|---|
| **互斥锁** mutex | 同一时刻只许一个线程进临界区 | 最常用；拿不到锁会**睡眠**（不适合中断上下文） |
| **自旋锁** spinlock | 拿不到锁就原地空转 | **不睡眠**，适合中断上下文/极短临界区；长等待浪费 CPU |
| **信号量** semaphore | 计数型，可做互斥也可做"资源计数" | 拿不到睡眠 |
| **原子操作** atomic | 对整型/位做不可分割的读写 | 无锁，适合简单计数、标志位 |
| 条件变量 | 等待某条件成立再继续 | 配互斥锁用 |

**死锁四条件**（必背）：互斥、占有且等待、不可剥夺、循环等待——破坏任意一条即可避免（工程上最常用：**统一加锁顺序**）。

**内核态版本**（嵌入式岗加分点）：内核里互斥锁叫 mutex（可睡眠），自旋锁 spinlock（不可睡眠）；**中断上下文绝对不能睡眠**——这就是"工作队列能不能睡眠"这道经典题的来源（见第 2 部分）。

## 1.4 用户态与内核态

- CPU 分两级权限：用户态（跑应用程序，不能直接碰硬件）和内核态（跑内核，什么都能碰）。
- 应用要碰硬件 → **系统调用**（syscall）陷入内核态，内核代办再返回。`read/write/open` 全是系统调用。
- **为什么这么设计**：隔离保护——应用崩了不死系统；硬件资源统一由内核仲裁。
- **机器人场景**：你在板子上 `echo 255 > /sys/class/leds/.../brightness`，就是用户态程序通过 sysfs 文件操作，触发内核里的 LED 驱动去拉 GPIO——一整条"用户态→系统调用→驱动→硬件"的链路你都亲手走过。

## 1.5 进程间通信（IPC 全家桶）

| 方式 | 特点 | 典型场景 |
|---|---|---|
| 管道/命名管道 | 单向字节流，亲缘进程/任意进程 | 简单命令组合 |
| 消息队列 | 有格式的消息块 | 松耦合同机通信 |
| **共享内存** | 最快（零拷贝，映射同一块物理内存） | 大数据量，**要配信号量/锁** |
| **socket** | 跨机器（也能本机：Unix 域套接字） | 分布式——**ROS2 的 DDS 底层就是网络 socket + 共享内存** |
| 信号 | 异步通知（如 SIGTERM 让进程退） | 生命周期管理 |
| 事件/回调类 | — | — |

**面试加分句**："ROS2 节点间通信底层是 DDS——同机时走共享内存/回环，跨机走 UDP 网络组播发现。所以 IPC 和网络编程是 ROS2 的地基，这就是为什么机器人岗狂考 Linux 原理。"

## 1.6 一切皆文件（你在板子上天天用的东西）

- `/dev`：设备节点（字符设备 c、块设备 b）——你的 `/dev/input/event5`（触摸）、`/dev/fb0`（显存）、`/dev/ttyS1`（串口）
- `/proc`：进程和内核状态的虚拟文件——`/proc/bus/input/devices`（你认设备名用的）
- `/sys`：设备和驱动的虚拟文件——`/sys/class/gpio/`（你拉功放脚用的）、`/sys/class/disp/`（你开彩条用的）
- **三者都是内核"投影"出来的，不在磁盘上**：读=问内核要状态，写=指挥内核。你已经用得很熟，面试时按这个讲。

## 1.7 网络编程基础（DDS 的地基）

- socket 编程模型：socket → bind → listen/accept（TCP 服务端）或 sendto/recvfrom（UDP）；TCP 可靠有序（重传、握手），UDP 快但无保证。
- **机器人场景**：多机协同（机器人+上位机）走 TCP/UDP；ROS2 的 DDS 默认用 **UDP 组播**做自动发现（同一网段的节点互相找到对方）——面试常问"两个 ROS2 节点互相发现不了怎么办"：先查是不是组播被交换机/防火墙挡了、是不是不在同一网段、再查 ROS_DOMAIN_ID 是否一致。

# 第 2 部分 · 嵌入式 Linux 与驱动（你的主场）

## 2.1 设备树（Device Tree）——你做过三次手术的地方

- **是什么**：描述硬件的文本文件（.dts 源码 → 编译成 .dtb 交给内核）。内核启动时读它，知道"什么硬件在哪个总线上、用什么参数"。
- **为什么存在**：同一份内核源码要跑在很多板上，板间差异全在设备树——**改硬件适配不用改内核代码**。这就是"驱动通用，板间差异全落设备树"。
- **匹配机制**（必考）：设备树节点的 `compatible` 字符串 ↔ 驱动源码里的匹配表（of_match_table）**一字不差**地对上 → 内核调用该驱动的 **probe 函数**（认领设备、初始化）。
- **pinctrl**：引脚复用配置也在设备树里（每根脚在同一时刻只能当一种功能用）。
- **你的实战案例**（面试现挂）：
  - 串口引脚从评估板的脚移植到本板的脚，功能编号查内核 pinctrl 驱动的引脚表确认
  - 触摸节点被一个旧节点"挡道"——内核用"全树第一个匹配名字的节点"，删幽灵节点解决
  - **软链接陷阱**：改了 dts 却不生效，因为 sed -i 把软链接改成了普通文件，"验证和编译读的是两个文件"

## 2.2 Linux 驱动框架（字符设备是入门必考）

- 三类设备：**字符设备**（按字节流顺序访问：串口、输入、显存——你项目里全是这类）、**块设备**（按块随机访问：存储）、**网络设备**（接口特殊，不走 /dev）。
- 字符设备三件套：设备号（主=驱动，次=同类下第几个）、`file_operations`（open/read/write/ioctl 函数指针表）、`/dev` 节点（用户态入口）。
- **平台总线模型**（嵌入式必考）：SoC 内部外设（I2C 控制器、串口控制器…）挂在虚拟的 platform 总线上，设备和驱动各自注册、按名字或 compatible 匹配后 probe——你的 GT9xx 触摸（I2C 客户端设备）和 LED（gpio-leds 平台设备）都走这套。
- **输入子系统**：触摸/按键驱动不用自己管"上报给谁"——向输入子系统注册，统一变成 /dev/input/eventX 事件流。你 hexdump 读过的 16 字节结构（type/code/value：EV_KEY 按键、EV_ABS 坐标、EV_SYN 帧分隔）就是它的协议。

## 2.3 中断（下半部机制是高频题）

- **中断上半部**：中断发生时内核立刻执行的那小段（中断处理函数）——**要求越短越好**，且**不能睡眠**（它不在进程上下文，睡了这个 CPU 就挂在这）。
- **下半部**：把耗时工作推迟到更宽松的环境做。三种机制：
  - **软中断** softirq：静态定义，性能最高（网络收包用）
  - **tasklet**：基于软中断，同一类不并发
  - **工作队列 workqueue**：跑在**进程上下文，可以睡眠**——这就是经典题"工作队列里能不能睡"的答案（能；而中断上半部和 tasklet 不能）
- **你的实战案例**：触摸芯片 INT 脚（PE5）触发中断 → 驱动在中断里只做"标记+调度"，读 I2C 坐标的慢活放下半部——面试讲这个流程，比背概念强。

## 2.4 交叉编译与内核模块（你做过三回）

- 交叉编译：在 x86 的电脑上，用 ARM 编译器，编译出 ARM 板能跑的程序。要点：工具链进 PATH、`STAGING_DIR`（目标板头文件和库的位置）、产物用 `file` 命令确认是 ARM 架构。
- 内核模块（.ko）：`obj-$(CONFIG_XXX)` 进 Makefile，Kconfig 加开关；`insmod/rmmod` 手动装卸，`/etc/modules.d/` + autoindex 开机自动装——你做 WiFi 驱动时踩过"编出来但进不了系统"的坑，解法是 OpenWrt 的 KernelPackage 机制（模块→包→系统清单三层）。
- **你顺手查证过的真功夫**（面试讲这个非常加分）：配置项 `CONFIG_GPIO_KEYS` 在内核源码里根本不存在（grep 零输出），写入配置被静默丢弃——**内核开关加了没效果，先查符号存不存在、再看 Kconfig 的 depends on 依赖链**。

# 第 3 部分 · 实时性（机器人控制绕不开）

## 3.1 软实时 vs 硬实时

- **硬实时**：超时=事故（电机控制 1ms 周期错过就是抖动/炸机）。 guarantees 最坏情况延迟。
- **软实时**：偶尔超时没关系（视频帧、语音）。
- 标准 Linux 是**软实时**：调度器追求吞吐公平，不保证"最坏多久能响应"。

## 3.2 PREEMPT_RT（实时补丁）——面试只要会说这几句

- **原理**：把内核里大量"不可抢占的区域"改小——中断处理**线程化**（中断也能被更高优先级任务抢占）、自旋锁改可抢占的实时锁、细化抢占点。
- **效果**：不提升平均性能，**把"最坏情况延迟"从几十毫秒压到几十微秒**且稳定。
- **现状**：2024 年起实时抢占代码已基本并入主线内核（6.12 起），说明这是官方认可的方向；Ubuntu 也有现成的实时内核包。
- **机器人场景**：运动控制线程跑在 RT 优先级，感知/规划跑普通优先级——"感知可以丢一帧，控制不能迟一拍"。

## 3.3 优先级反转与优先级继承（经典题）

- **优先级反转**：低优先级任务拿着锁，高优先级任务等锁，中等优先级任务却插队跑——高等低、低被中抢，最坏情况被中等的拖长。
- **解法：优先级继承**——低任务持锁期间，临时把它的优先级提到等锁的最高优先级，让它赶紧跑完放锁。
- **名场面**：1997 年火星探路者号在火星上反复重启，就是优先级反转没处理——面试讲这个故事，记忆点拉满。

## 3.4 实时总线一句话定位

- **CAN**：汽车/机器人电机主流，多主、差分、抗干扰、带宽低（最高 1 Mbps）但可靠有优先级仲裁。
- **EtherCAT**：工业级，百 Mbps，百微秒级同步，贵——大型机械臂/高端设备用。

# 第 4 部分 · ROS2（机器人软件框架，你的待补区）

## 4.1 为什么是 ROS2 而不是 ROS1（必考）

| | ROS1 | ROS2 |
|---|---|---|
| 架构 | **中心化**：必须有一个 Master（名字服务），Master 挂全挂 | **去中心化**：节点互相自动发现（DDS 组播），无单点故障 |
| 通信 | 自定义协议 | 标准化 **DDS** 中间件 |
| 实时性 | 基本没有 | DDS 支持实时 QoS |
| 平台 | 只支持 Linux | Linux/Windows/macOS/**嵌入式 MCU** |
| 生命周期 | ROS1 已停止维护（EOL） | Humble/Jazzy 持续维护，行业新项目默认 ROS2 |

## 4.2 三种通信方式（必考，要会按场景选）

| 方式 | 模型 | 适合 | 机器人例子 |
|---|---|---|---|
| **话题 Topic** | 发布/订阅，**单向流式**，多对多 | 持续不断的数据 | 相机图像流、激光雷达点云、IMU 数据、电机速度指令 |
| **服务 Service** | 请求/响应，**一问一答**，同步等待 | 一次性查询/设置 | "计算器给我算一下""读取当前电量" |
| **动作 Action** | 长时任务，**目标→反馈→结果**三段，可取消 | 耗时任务要过程反馈 | "导航去 A 点"（途中持续反馈位置，可中途取消）、机械臂运动到某位姿 |

**记忆口诀**：数据流用话题，问答用服务，干长活带进度条用动作。

## 4.3 DDS 与 QoS（区分度题，答好显专业）

- **DDS**：数据分发服务标准。ROS2 不自己造通信，直接用工业级 DDS（常见实现 Fast DDS、CycloneDDS）——同一网段节点通过组播**自动发现**彼此。
- **QoS（服务质量）策略**（高频）：
  - **可靠性**：Reliable（可靠重传，丢不得，如导航目标）/ BestEffort（尽力而为，丢帧没事，如传感器流）
  - **历史/深度** History+Depth：队列存几条，满了丢最老的（KEEP_LAST）还是全存（KEEP_ALL）
  - **持久性** Durability：晚加入的订阅者能不能收到之前发的消息
- **经典坑题**："发布端是 BestEffort，订阅端是 Reliable，为什么收不到消息？"——**QoS 不兼容**：订阅端要求可靠，发布端给不了，DDS 直接不建立连接。**兼容规则：订阅端的要求 ≤ 发布端提供的才行。**
- **面试常问排查题**："两个节点互相收不到消息？"排查顺序：①两边是否同一个 ROS_DOMAIN_ID（不同域互相看不见）②QoS 是否不兼容 ③组播是否被网络挡住（DDS 靠组播发现）④时间是否同步。

## 4.4 常用工具与概念（知道名字和用途）

- **launch**：Python 写的启动脚本，一次拉起一堆节点并配参数、remap
- **tf2**：坐标变换树——机器人身上十几个坐标系（基座、各关节、雷达、相机）之间的平移旋转关系，谁发布、谁查询；"tf 树断了"是机器人调试日常
- **rosbag**：录数据/回放数据（传感器数据录制，离线重放调试）
- **参数系统**：节点参数可声明、读取、动态设置
- **URDF**：机器人的结构描述文件（连杆、关节、惯量），仿真和 tf 都靠它

## 4.5 机器人软件骨架（把工具串成系统）

```
传感器层（雷达/相机/IMU 驱动节点）
   ↓ 话题（原始数据）
感知层（定位 SLAM、障碍识别）
   ↓ 话题（位姿、地图、障碍）
规划层（全局路径 + 局部避障）
   ↓ 话题（速度指令 cmd_vel）
控制层（差速/麦克纳姆轮解算 → 电机）
   ↓ 总线（CAN/串口）
硬件层（电机驱动器）
```
贯穿全系统的横线：tf 坐标树、参数、日志、launch 编排。**面试讲系统设计，就按这个骨架从上往下说。**

# 第 5 部分 · 把 T113 项目讲成面试项目（最重要的一节）

## 5.1 电梯陈述（30 秒版，背下来）

> "我在一块全志 T113 的开发板上完整做过一次嵌入式 Linux 的板级适配：从零开始调通调试串口，然后逐个点亮 GPIO、I2C 触摸、MIPI 屏幕、音频、WiFi 和蓝牙，最后在板子上跑起 LVGL 图形界面、手机能把它当蓝牙音箱用。整个过程涉及 U-Boot、内核配置、设备树、交叉编译和驱动调试，全部问题靠日志和抓包定位，有完整的问题档案。"

## 5.2 两分钟版结构（项目叙述的骨架）

1. **背景**：一块非官方参考设计的板子，官方软件配的是评估板，硬件接线不同——本质是"让软件配置匹配实际硬件"的移植工程
2. **流程**：调试串口（系统地基）→ 外设逐个点亮 → 无线 → 图形
3. **方法**：每个问题都是"证据定位"——串口日志、内核抓包、源码查证，不瞎试
4. **结果**：8 项外设全通 + 15 个问题的完整档案（有文档仓库可展示）

## 5.3 关卡 ↔ 考点映射（面试官从你项目里会追问什么）

| 你做的 | 表面的考点 | 深一层的考点（准备好） |
|---|---|---|
| 调试串口移植 | 启动流程、串口 | 为什么改三处（三阶段各读各的配置）；earlycon 原理 |
| LED/按键 | GPIO、内核配置依赖 | config 开功能 / dts 接硬件的分工；孤儿节点 |
| 触摸 | I2C、输入子系统 | 设备树 compatible 匹配与 probe；输入事件结构 |
| 显示 | 帧缓冲、显示管线 | fb 与面板尺寸；U-Boot 与内核的分工 |
| 音频 | ALSA | 混音器控件；使能脚极性查手册 |
| WiFi | SDIO、内核模块 | 模块→包→系统三层（KernelPackage） |
| 蓝牙 | HCI/协议栈、串口带宽 | 带宽定量分析（见 5.4） |
| LVGL | 帧缓冲渲染 | 无屏验证方法（dump 显存）——体现工程巧思 |

## 5.4 三个"亮点故事"（面试的杀手锏，每个 1 分钟）

**故事一：带宽算账（蓝牙音箱卡顿）**
"手机连板子放歌一卡一卡。我没有瞎试，先算账：实测串口每秒到达 10.2 KB，立体声音乐需要 41 KB——管道只有需求的四分之一，数据必然断流。提速路线（改芯片波特率）失败后走降流量路线：修改音频协商程序源码，让板子只广播低码率能力，手机按规范只能选低的——从源头压流量，最终流畅。**方法论的点**：定量分析先于动手，10.2 对 41 这两个数字直接决定了路线取舍。"

**故事二：配对快照机制**
"手机蓝牙连不上音箱，剥了五层洋葱：缺配对应答、应答能力声明错、服务注册丢失、对端缓存过期、服务记录缺失。每层都是抓包实锤，不是猜的。最后沉淀出一个可复用的机制认知：**对端的功能清单是配对那一刻的快照，板子事后补的服务对方不知道，必须删配对重配**。"

**故事三：内核开关查证**
"内核配置加了没效果，我没有接受'多加几个试试'——去源码里查证，发现其中一个开关在内核源码里**根本不存在**（写入被静默丢弃），真正需要的是另一个只依赖基础库的开关。**方法论的点**：内核开关加了没效果 = 依赖没满足或符号不存在，沿 Kconfig 的依赖链查证，不猜。"

## 5.5 面试官追问的深水区（提前备好接法）

| 追问 | 接法 |
|---|---|
| "你这个项目有实时性要求吗？" | 诚实说没有硬实时场景（音视频都是软实时），然后**主动讲**了解的 PREEMPT_RT 和优先级反转（第 3 部分兜住） |
| "你会 ROS2 吗？" | "正在学，装了 Humble 跑通了话题通信和 launch。我的理解是 ROS2 底层 DDS 就是 IPC+网络编程的工业化实现，我 Linux 底层的底子能直接迁移"——诚实+展示迁移能力 |
| "遇到最难的问题是什么？" | 讲故事二（五层洋葱）——展示定位深度和耐心 |
| "为什么改配置不生效这种坑你能踩？" | 讲软链接陷阱（验证和编译读的是两个文件）——展示复盘能力，把坑变成方法论 |
