**我看到的**（两页拼起来）：

第7页触摸FPC座（8脚）：
```
1=GND  2=TP_RST  3=TP_SCL  4=TP_SDA  6=TP_INT  (5,7,8=3V3/GND)
```

第1页PE组（用PyMuPDF渲染6倍放大图看清的）：

| T113引脚(球脚号) | 网络名 | 角色 |
|---|---|---|
| **PE5** (42) | TP_INT | 触摸中断（手指按下时芯片拉它通知CPU） |
| **PE4** (43) | TP_RST | 触摸复位/唤醒 |
| **PE0** (44) | TP_SCL | I2C时钟线 |
| **PE1** (45) | TP_SDA | I2C数据线 |

**为什么这步**：引脚配错=全盘皆输（本轮最大坑就在这）。必须先拿原理图锁死硬件事实，再写设备树。

**加分项——这四条线怎么进芯片的（数据手册+内核C表）**：
```
VM里跑：grep -A8 'PINCTRL_PIN(E, 0)' kernel/linux-5.4/drivers/pinctrl/sunxi/pinctrl-sun8iw20.c
输出（关键行）：
  PE0: SUNXI_FUNCTION(0x4, "twi1"),   /* SCK */   ← PE0的功能4就是TWI1时钟
  PE1: SUNXI_FUNCTION(0x4, "twi1"),   /* SDA */
  PE4: SUNXI_FUNCTION(0x4, "twi2"),   /* SCK */   ← PE4/PE5本可当TWI2，但板上拿它当GPIO用
  PE5: SUNXI_FUNCTION(0x4, "twi2"),   /* SDA */
  PE14: SUNXI_FUNCTION(0x2, "twi1"),  /* SCK */   ← 注意！TWI1还有第二组引脚PE14/15
  PE15: SUNXI_FUNCTION(0x2, "twi1"),  /* SDA */
```
**结论**：TWI1控制器有**两组可选引脚**（PE0/PE1 和 PE14/PE15）。原理图实锤本板用 **PE0/PE1**。这就是后面"引脚错位案"的伏笔——板级包dts默认配的是PE14/15！

### 6. 读懂原始事件：hexdump解码（答辩必备功力）

**命令**：`hexdump -C /dev/input/event5`，然后按住屏幕滑动、松手，Ctrl+C。

**16字节=1个事件**（struct input_event，32位ARM布局）：

| 字节偏移 | 0-3 | 4-7 | 8-9 | 10-11 | 12-15 |
|---|---|---|---|---|---|
| 含义 | tv_sec | tv_usec | type | code | value |
| 我的数据 | `89 40 00 00` | `fe 87 02 00` | 事件类型 | 哪个轴 | 数值(小端) |

**type/code速查**（从我们的数据里归纳）：
| type | code | 含义 |
|---|---|---|
| `01 00`(EV_KEY) | `4a 01`(BTN_TOUCH) | value=1按下 / 0抬起 |
| `03 00`(EV_ABS) | `35 00` | ABS_MT_POSITION_X（X坐标） |
| `03 00` | `36 00` | ABS_MT_POSITION_Y |
| `03 00` | `30 00`/`32 00` | 触点椭圆长轴/宽（接触面积） |
| `03 00` | `39 00` | ABS_MT_TRACKING_ID（多点协议B的触点身份证） |
| `00 00`(EV_SYN) | `02 00`/`00 00` | SYN_MT_REPORT/SYN_REPORT 一帧结束 |

**实测数据逐行读**（我们抓到的第一触点）：
```
01 00 4a 01 01 00 00 00 → BTN_TOUCH = 1        手指按下！
03 00 35 00 a8 00 00 00 → X = 0xa8 = 168       手指在屏幕x=168处
03 00 36 00 1d 02 00 00 → Y = 0x21d = 541      y=541
03 00 39 00 00 00 00 00 → TRACKING_ID = 0      这是0号触点
00 00 02 00 ... 00 00 00 00 → SYN              一帧上报完毕
```
按住不动：时间戳在走（tv_sec `89 40`→`8a 40`→`8b 40`），坐标每帧重复=手指没动。**滑动实锤**：第二触点X从167一路降到149、Y从139涨到506——一条往左下的斜线，内核忠实地记录了轨迹！最后 `01 00 4a 01 00 00 00 00` = BTN_TOUCH=0 松手。

**坐标反向验证屏幕尺寸**：Y最大观察到629 < 720，若屏真是960×320则Y=629早就越界——**实证屏幕是720×720**，反过来校准了设备树里的`ctp_screen_max_x/y=0x2D0`。

**通用心法（本次新增）**：
1. **"枚举到"≠"应答了"**：dts声明的i2c client一定存在，芯片应答要靠probe时真通信。别被`2-0014 exists`骗了。
2. **控制器开对≠线接对**：TWI1有多组引脚，pinctrl配哪组波形就从哪组出。**C表查功能号+原理图查走线，两边都要对**。
3. **报错提示语也会骗人**（"please set sys_config.fex"是过时文案），信源永远以代码路径为准。
4. dts批量修改用**python锚点校验**（先assert行内容再改），不用裸sed（&转义坑）。

### 8. 师傅拷打预演（触摸方向）

**Q: 为什么触摸用I2C不是SPI？** A: GT9xx这颗芯片本身就只出I2C接口；触摸数据量小（每帧几十字节）、对速率不敏感，400kHz I2C足够，还省引脚（2根数据线+INT+RST共4根）。SPI常见于大屏高速驱动IC（如ili9881这类屏驱）。

**Q: 0x5D和0x14怎么选？** A: GT9xx上电时序里INT脚的电平决定地址：INT高=0x5D（0xBA写/0xBB读），INT低=0x14（0x28/0x29）。本板实测0x5D应答（老师的参考dts也是0x5D）。若烧0x14版本会满屏ACK not received。

**Q: ctp_screen_max_x/y是干嘛的？缺了会怎样？** A: 驱动把芯片原始坐标缩放映射到屏幕分辨率用的上限。缺了/为0时`ctp_get_system_config()`直接return 0，probe失败——这是源码里写死的。

**Q: cat event5看到的数据和屏幕坐标什么关系？** A: 16字节一个input_event，type/code/value三段式；`03 00 35 00 + value`是X轴绝对坐标（720分度），`36 00`是Y。EV_SYN是一帧的句号。多点触摸B协议用TRACKING_ID区分同时按下的多根手指。

**Q: 为什么INT脚还要配成GPIO？I2C不是能轮询吗？** A: 轮询浪费CPU且延迟不稳定。INT是芯片主动通知："有新数据了"。驱动申请中断，手指按下触发中断服务程序再去I2C读坐标——事件驱动，又快又省。

**fix_twi1_pins.py（手术③：引脚组改PE0/PE1）**——只动twi1_pins_a/b块内部的pins行，块外其他PE14/15（gmac0等）一概不碰：
```python
def fix_block(tag):
    start = 找到含tag的行
    for j in range(start, start+8):              # 只在块头后8行内找
        if 'pins' in lines[j] and 'PE14' in lines[j]:
            lines[j] = lines[j].replace('"PE14", "PE15"', '"PE0", "PE1"')
            return
    raise SystemExit(tag + ': pins line not found')   # 找不到就报错停，不硬来
fix_block('twi1_pins_a: twi1@0')
fix_block('twi1_pins_b: twi1@1')
```

**为什么用python不用sed**：dts里有`<&pio PE 5 GPIO_ACTIVE_HIGH>`这类含特殊字符的文本，GNU sed替换串里`&`代表"整个匹配内容"会炸出双份坏行（考核②已踩过）；python的str.replace所见即所得，且配合锚点assert=手术刀级安全。
