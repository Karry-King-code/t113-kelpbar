# 蓝牙问题排查全记录 —— 从芯片起不来到手机放歌流畅收工

> **这份文档记什么**：T113 KelpBar 蓝牙任务（蓝牙 + 蓝牙播音乐 8.5）从 2026-10-12 到 10-14 全部**实际发生的报错、排查指令、根因与修法**。
> 每个问题都按 **症状 → 实际报错 → 排查过程 → 根因 → 修复 → 验证** 六段写，命令可直接复制。
> 时间线四幕：**① 芯片起不来 → ② SPP 串口业务 → ③ A2DP 五层坑 → ④ A2DP 卡顿（带宽之战）**。

---

## 0. 硬件背景：蓝牙到底接在哪（先看清楚再排障）

### 0.1 芯片与链路

| 项目 | 值 | 出处 |
|---|---|---|
| 芯片 | RTL8723DS（WiFi + BT 二合一） | SDIO VID:PID `024c:d723`（WiFi 半边实测） |
| BT 走的口 | **UART1**（`/dev/ttyS1`），**H5 协议**（3-wire） | 原理图 PG6–PG9 直连模组 |
| BT 引脚 | TX=PG6 / RX=PG7 / RTS=PG8 / CTS=PG9 | 原理图（下图） |
| 固件 | `/lib/firmware/rtlbt/rtl8723d_fw` + `rtl8723d_config`（41 字节配置） | Realtek 标准布局 |
| 加载器 | `rtk_hciattach -n -s 115200 /dev/ttyS1 rtk_h5` | 静态交叉编译，源码 github plow-technologies/rtl8723ds_bt |
| 板子蓝牙地址 | `34:75:63:48:4A:AD`（设备名 T113-KelpBar） | `btmgmt info` |

![蓝牙 UART1 走线：PG6-PG9](images/bt_uart1_pg6-9.png)

**这张原理图要记住两件事**（后面两幕的坑都从这里来）：

1. **PG6–PG9 是芯片到 WiFi+BT 模组的 PCB 内部走线**，板上没有任何测试点/排针能引出来——所以"用逻辑分析仪抓 UART 波形"这条路物理上不存在，只能靠软件侧证据（btmon 抓包、日志）定位。
2. **RTS/CTS（PG8/PG9）在板子上没有复用连接**——一旦让芯片开启硬件流控，它等 CTS 等到死。第四幕 1.5M 提速失败的埋伏就在这。

### 0.2 工作机制：rtk_hciattach 每次开机都在干什么

```
上电 → rtk_hciattach 以 115200 打开 /dev/ttyS1
     → 发 H5 sync 同步
     → 读 rtl8723d_config（若存在）→ 按 config 里的波特率/流控位发 change-speed
     → 把 rtl8723d_fw 固件补丁下载进芯片 RAM
     → 芯片重启协议栈 → hci0 出现（约 4 秒）
```

**推论**：芯片里的固件和配置**每次断电都丢**（RAM），每次开机重新下载——所以"改 config 文件"改的是**下载行为**，不是芯片本身；也所以**任何把下载过程打断的操作都可能让芯片卡在中间状态**（后文"芯片假死"）。

## 第一幕：蓝牙芯片起不来（适配期）

### 问题 1：固件补丁下载一直超时

**症状**：`rtk_hciattach` 卡住，hci0 迟迟不出。

**实际报错**（串口日志原文）：

```
patch timerout, retry
3-wire download patch re send:1
3-wire download patch re send:2
...（一路重发到 40）
H5 patch timed out
```

**排查**：去看 config 文件里到底写了什么。`rtl8723d_config` 共 41 字节，其中：
- **data[0:4]**：芯片应切换到的波特率，小端 32 位。原版值为 `0x04928002` 附近的一组 H5 编码，指示切到 **4,928,002 波特 + 硬件流控**。
- **data[12]**：流控等标志位，bit2 = 硬件流控开关。

**根因**：原版 config 指示芯片切 **4.9M 波特**并开硬件流控。T113 的 UART1 上限 1.5M，根本跟不上；而且 PG8/PG9（CTS/RTS）板上没连，流控一开芯片等 CTS 等到死。下载必然超时。

**修复**：**删除 `/lib/firmware/rtlbt/rtl8723d_config`**。没有 config，rtk_hciattach 走默认路径：全程 115200、无流控，稳定下载成功，hci0 约 4 秒出现。

> **为什么敢删**：config 只影响"下载固件时的串口参数"，fw 本体还在。115200 慢是慢（下载多花两秒），但每一步都在协议能力范围内。
> **这句话反过来说就是第四幕的主题**：115200 稳，但带宽只有 11.5KB/s——蓝牙能连上，跑不动大流量。

### 问题 2：手机报"配对码不匹配"

**症状**：手机发起配对，弹 PIN 码输入框/报配对码错误。

**根因**：没开 SSP（Secure Simple Pairing），协议栈回落到传统 PIN 配对。

**修复**：

```sh
btmgmt ssp on          # 打开 Secure Simple Pairing
btmgmt io-cap 3        # IO 能力 = NoInputNoOutput → Just Works 免确认配对
```

`io-cap 3` 的含义：板子没有屏幕没有键盘，声明"我没有输入输出能力"，配对自动走 Just Works，手机上直接弹"配对"按钮，不用输码。

### 问题 3：手机报"已拒绝配对"

**根因**：`bondable` 没开。配对=交换密钥建立绑定，bondable off 时协议栈直接拒绝。

```sh
btmgmt bondable on
```

### 问题 4：手机/电脑搜不到 T113-KelpBar

**排查**：`hciconfig hci0` 看 flags，`btmgmt info` 看 class。

**根因**：**COD（Class of Device）= 0x000000**。class 为 0 的设备会被安卓/Windows 的扫描过滤器直接隐藏——不是射频问题，是对端"看见了但装没看见"。

**修复**：

```sh
hciconfig hci0 class 0x000104    # 少数设备类，保证可见（后续改为 0x240404 音频类，见第三幕）
hciconfig hci0 piscan            # page scan + inquiry scan 都开
btmgmt discoverable on
btmgmt connectable on
btmgmt name T113-KelpBar
```

> ⚠️ 这台 Realtek 固件有个怪癖：`hciconfig hci0 class` **读回为空**（不回读），别以为没写进去——以 `btmgmt info` 显示的 class 为准，或直接用手机扫一遍验证。

### 问题 5：芯片假死（attach 报 IC: NONE）

**症状**：重新 attach 时报：

```
LMP Subversion 0x675f / EVersion 2 / IC: NONE
找 rtl_none_fw ...
```

正常应识别为 `IC: RTL8723DS`（LMP Subversion 0x8723）。`IC: NONE` = 芯片处于半初始化状态，H5 会话卡死。

**实测结论**（每条都踩过）：
- `rmmod`、`rfkill block/unblock`、软重启（`reboot`）——**全部救不回来**。
- **唯一解法：整机断电 15 秒**。BT 供电域是 VBAT 常供电，只要板子有电芯片就保持着坏状态。

**衍生铁律**：**手机连着放歌时绝不能 `killall rtk_hciattach`**（实际发生过：kill 后芯片 H5 会话卡死 → 7 个波特率全扫无应答 → 只能断电）。要先断开蓝牙连接再动进程。

### 第一幕小结：成功配方（五个条件缺一不可）

| # | 条件 | 缺了会怎样 |
|---|---|---|
| 1 | **芯片冷启动**：断电 15 秒再上电 | 假死芯片怎么 attach 都 `IC: NONE` |
| 2 | **移除 `/lib/firmware/rtlbt/rtl8723d_config`** | 固件下载超时（4.9M 波特+流控超出板子能力） |
| 3 | `btmgmt ssp on` + `btmgmt io-cap 3` | 走传统 PIN →"配对码不匹配" |
| 4 | `btmgmt bondable on` | "已拒绝配对" |
| 5 | `hciconfig hci0 class 0x000104`（后改 0x240404） | class=0 → 安卓/Windows 直接隐藏 → 搜不到 |

一键脚本 `/etc/bt_up.sh`（开机自启，走 rc.local）把这五步 + SDP 注册固化，另有 `/root/bt_up.sh` 双备份（为什么放两份见第四幕"断电吞文件"）。

## 第二幕：SPP 串口业务（电脑 ↔ 板子双向回显）

> 背景：导师指出"**配对 ≠ 连接**"——配对只是交换密钥，连接才是跑业务。SPP（蓝牙串口）是最直接的业务验证：电脑通过蓝牙虚拟串口连板子，发一行、板子回一行。

### 问题 6：sdptool 报 Failed to connect to SDP server

**实际报错**：

```
Failed to connect to SDP server on FF:FF:FF:00:00:00: Connection refused
```

**根因**：这台 Tina 的 BlueZ 5.54 里，`/var/run/sdp` 套接字**只有 bluetoothd 以兼容模式启动才创建**。

**修复**：bluetoothd 必须 `-C` 启动：

```sh
bluetoothd -n -C        # -C = compat 模式，创建 /var/run/sdp，sdptool 才有得连
```

**注册 SPP 服务记录**：

```sh
sdptool add --channel=3 SP          # 输出 Serial Port service registered
sdptool browse local | grep -A3 'Serial Port'   # 自检：Service Name / Channel: 3
```

> **SDP 记录只存在 bluetoothd 内存里**，每次开机都要重新 add——这就是 bt_up.sh 里必须有这一步的原因。

### 问题 7：Can't create RFCOMM TTY: Address already in use

**症状**：ACL 已连上（`hcitool con` 可见）、通道号也对，但内核建不出 `/dev/rfcomm0`，电脑写数据超时。

**排查**：

```sh
ls /sys/class/tty | grep rfcomm     # 出现 rfcomm0 = 0 号被内核占位
```

**根因**：被 kill 过的 rfcomm 进程会在**内核留下 dev id 占位**。设备节点删了（`rm /dev/rfcomm0`）也没用——占位在内核内存里。rfcomm1~8 依次试完自动消失，只剩被占的那个一直挂着。

**修复**：
- 临时：脚本里用 `auto` 让它自动跳到下一个空闲编号（实测跳到 rfcomm1 能用）；
- 彻底：**重启板子**。重启后占位清除，auto 自然回到 rfcomm0（真实重启后实测验证）。

### 问题 8：回显内容被污染（多出 ^J）

**根因**：板上 busybox **没有 stty**，rfcomm tty 默认带回显，对方发来的字节被 tty 层弹回一份。

**修复**：rfcomm 用 `-r`（`--raw`）关掉 tty 层处理：

```sh
rfcomm -r listen /dev/rfcomm0 3 &
```

业务脚本 `/etc/spp_demo2.sh` 两段式：先 `rfcomm -r listen` 建 tty，独立循环检测 tty 出现后发问候语 + `read` 循环回显（收到 `xxx` 回 `T113-Echo: xxx`），断线自动重新监听。

### 问题 9：电脑连上服务但数据发不出（0x80072743）

**症状**：Windows 侧 WinRT `StreamSocket.ConnectAsync` 报 **`0x80072743`（WSAENETUNREACH 网络不可达）**。

**排查**（关键一步，btmon 抓包）：

```sh
btmon -w /tmp/btmon_cap.btsnoop     # 抓全程，回放 btmon -r
```

抓包实锤：电脑连接后**只做了 SDP 查询（L2CAP PSM 1），完全没有发起 RFCOMM 连接（PSM 3）**——包根本没到建链那一步，所以是电脑"不知道该连哪"。

**根因**：**电脑在配对那一刻缓存了板子的服务列表**，而 SPP/A2DP 服务是**配对之后**才注册的——电脑的缓存里没有这些服务，自然不知道要发起 RFCOMM。

**修复**：**删除配对记录 → 重新配对**。重配时电脑重新查 SDP，这次能看到 Serial Port，COM 口才能建出来。

> ★ **核心机制（全篇最重要的一条，后面还要用两次）**：
> **安卓/Windows 的 profile 列表 = 配对那一刻的 SDP 快照。板子侧事后补注册服务，对端不会自动知道，必须删配对重配才能刷新。**
> 固定顺序：**先修好板子服务，再让对端重新配对**。反过来（先配对后修服务）= 白配。

### 问题 10：Windows 出现两个蓝牙串口，用哪个

配对成功后 Windows 设备管理器出现两个 COM 口：

| COM 口特征 | 身份 | 能不能用 |
|---|---|---|
| InstanceId 含 `_LOCALMFG&0000` | **本机自己的入口** | ✗（实测写进去没反应） |
| InstanceId 含板子地址 `347563484AAD` | **通往板子的出口** | ✓ |

查法：

```powershell
Get-PnpDevice -Class Ports | ? {$_.InstanceId -like '*BTHENUM*'} | fl
```

任何串口工具 115200-8N1 打开"出口"COM 口，即见板子问候语，双向回显通。
（实测本机：入口 COM8 别用，出口 **COM9**。）

### 问题 11：H5 序列号告警（噪音，非阻断）

**实际报错**（dmesg）：

```
Bluetooth: Out-of-order packet arrived (5 != 6)
__hci_init err=-56 EIO
```

**结论**：H5 滑窗序列号错乱，内核态重试后恢复，**不阻断连接**。记录在案：出现这条不用慌，先看业务通不通，别被日志带偏。

### 第二幕验收（含金量最高的一次）

板子**真实重启**（非手动拉起），30 秒后电脑零操作直连：

```
/tmp/bt_boot.log: [3/6] bluetoothd -n -C / SDP socket 就绪
                  [5/6] bluealsa + bluealsa-aplay 已启动
                  [6/6] Serial Port service registered
电脑发 HELLO_FROM_WINDOWS_PC → 板回 T113-Echo: HELLO_FROM_WINDOWS_PC
```

自检法：重启后等 30 秒 → `cat /tmp/spp_events.log` 应见 `spp_demo2 start`；`hciconfig hci0` 应为 `UP RUNNING PSCAN ISCAN`。

## 第三幕：A2DP 手机连不上（五层坑，逐层剥开）

> 背景：SPP 通了之后做蓝牙音箱（A2DP Sink）：手机把 T113 当蓝牙音箱放歌。
> 链路：`手机 --A2DP--> bluealsa --> 声卡 audiocodec --> HPOUT --> LM4871 功放 --> CN2 喇叭`。

### 层 1：Authentication attempt without agent

**症状**：手机蓝牙详情页有「媒体音频」开关、也打开了，但状态永远「已保存」，连不上，没声音。
**先说结论：「已保存」= 没连上 = 没有音频通路，听不到。**

**实际报错**（`tail /tmp/bluetoothd.log`，三条日志直接定案）：

```
Endpoint registered: /org/bluez/hci0/A2DP/SBC/sink/1   ← 音箱服务本身是好的
Authentication attempt without agent                    ← 有人来连，要找 agent 确认鉴权
Access denied: org.bluez.Error.Rejected                 ← 没人应答，bluetoothd 自己拒了
```

**根因**：板上**没有配对 agent**。对方来连接时 bluetoothd 要找人确认这次鉴权，找不到人 = 一律拒绝。

**为什么串口能连、音乐不能**：rfcomm 监听**不要求鉴权**；A2DP 音频**必须鉴权/加密**。这一个差别解释了全部现象。

**第二层根因（更隐蔽）**：`/var/lib/bluetooth/` **根本不存在**。之前那次"配对成功"是 `btmgmt` 在**内核/芯片层**做的，bluetoothd 完全不知情；芯片固件每次开机重新下载，芯片里那份密钥也随之丢失。
→ **一般规律：`btmgmt` 配的对 ≠ bluetoothd 知道的对。要走 profile（音频），必须让 bluetoothd 参与配对**，密钥落到它的数据库（这台 Tina 实际落在 **`/etc/lib/bluetooth/<适配器>/<MAC>/info`**，overlay 分区，重启不丢）。

**修复**：新增 `/etc/bt_agent.sh`，由 bt_up.sh 拉起（后台化）：

```sh
{ printf 'agent NoInputNoOutput\ndefault-agent\npairable on\ndiscoverable on\n';
  while true; do sleep 3600; done; } | bluetoothctl
```

启动方式：

```sh
rm -f /var/run/btagent.pid
start-stop-daemon -S -b -m -p /var/run/btagent.pid -x /bin/sh -- /etc/bt_agent.sh
```

两个细节：
- **管道尾部的 `sleep 3600` 是关键**：bluetoothctl 一退出，agent 注册即消失，连接又被拒。必须占住管道读端。
- **手动调试起服务一律用 `start-stop-daemon -S -b`**：adb 会话断开时会杀掉会话内用 `&` 起的后台进程（实测 bluealsa 就这样死过；开机路径因父进程是 init 才幸存）。

### 层 2：agent 在，手机却报"PIN 码或密钥不正确"

**症状**：agent 脚本在跑，手机配对仍失败，报「PIN 码或密钥不正确」。

**btmon 抓包还原完整失败链**：

```
手机发起 SSP（IO 能力交换）→ 板子回应 DisplayYesNo
→ Numeric Comparison 流程 → User Confirmation Request (passkey 014117)
→ 30 秒无人确认 → Authentication Failed
```

**根因**：板子宣称的 agent 能力是 **DisplayYesNo**（要人按确认），不是 NoInputNoOutput。30 秒没人确认就超时。**手机报的"PIN 码不正确"是误导——真相是板子没人应答确认，不是密钥错。**

**为什么板子会宣称 DisplayYesNo**（这层最坑）：bluetoothctl **启动时会自动注册一个 KeyboardDisplay 能力的 agent**——脚本里后续喂的 `agent NoInputNoOutput` 根本没生效（日志 `Agent is already registered` 实锤）。
**另一个坑**：任何手工 bluetoothctl 会话（**哪怕只是进去敲 `version` 排查**）都会注册自己的 agent 并抢走 default-agent，退出后角色悬空。

**修复**：
1. 用**启动参数**直接指定能力，不走交互命令：

```sh
bluetoothctl --agent NoInputNoOutput
```

2. 自愈循环：管道里每 30 秒重发一次 `default-agent`，被抢了就夺回来。
3. 排查纪律：**查 agent 状态只用 btmon/btmgmt，不要跑 bluetoothctl**（跑一次污染一次）。
4. 给已配对设备加信任（未受信设备连 profile 还会被盘问；`trust` 不抢 default-agent）：

```sh
printf 'trust 7C:A4:49:2C:A6:6D\n' | bluetoothctl    # 手机
printf 'trust 14:B5:CD:71:99:D8\n' | bluetoothctl    # 电脑
```

### 层 3：双配对成功，但"只能配对、无法连接"

**症状**：电脑、手机都配对成功（`/etc/lib/bluetooth` 下两份 info 都有 [LinkKey]），点连接却连不上。

**btmon 抓包**：对方连接后**只做了 SDP 查询就走了，没发起 AVDTP（PSM 25）**——它在查"你是音频接收设备吗"，查出来是空。

**排查**：`sdptool browse local` 只剩 AVRCP×2 + SPP，**Audio Sink 记录丢了**。
> ⚠️ 顺带一个工具坑：`sdptool browse local` 在这块板上**不可靠**——连续两次查询结果互相矛盾（一次有 AudioSink 没 SPP，一次反过来），"local"甚至被解析成远端 PC 地址。**这个输出不能当判断依据**；可信的是 bluetoothd 日志的 `Endpoint registered` 和对方的真实连接行为。

**根因**：bluealsa 向 bluetoothd 注册的 A2DP 端点在反复折腾蓝牙状态的过程中被弄掉了（端点注册是活的，bluealsa 死了/被重启过就没了）。

**修复**：重启 bluealsa 重新注册：

```sh
killall bluealsa bluealsa-aplay
start-stop-daemon -S -b -x /usr/bin/bluealsa -- -p a2dp-sink --a2dp-volume -i hci0
start-stop-daemon -S -b -x /usr/bin/bluealsa-aplay -- --profile-a2dp 00:00:00:00:00:00
# 验证：bluetoothd 日志重新出现 Endpoint registered ×2
```

**连带修复**：重启 bluetoothd 后 SDP 记录也会清空，要重补（见层 5 的完整重启序列）。

### 层 4：手机重配后详情页没有「媒体音频」开关

**症状**：手机删配对重配，详情页只有「联系人信息和通话记录分享」，**连媒体音频开关都没有**。

**判读**：手机这次配对发生的时间点，正好落在层 3（Audio Sink 记录丢失）期间——**配对快照机制**（见问题 9 的★）：安卓在配对那一刻查 SDP 并缓存 profile 列表，缓存里没有音频，之后板上服务修好了手机也不知道。

**修复**：先修板子（层 3/层 5），**再**删配对重配。顺序不能反。

### 层 5（最后一层）：SDP 空应答实锤 → 手动补 A2SNK

**症状**：板侧服务明明都重启好了（bluetoothd 日志有 Endpoint registered），手机再重配，**还是没有媒体音频开关**。

**铁证**（btmon 抓包 + PC 端解析 btsnoop 里的 SDP 应答）：

```
手机配对时的 SDP SSA 查询序列：
  Service Search Attribute Response len 5   ← 5 字节 = 0 条记录匹配
```

手机问"你是音频接收设备吗"，板子答**空**。同窗口里 SPP/AVRCP 记录都在（79B/427B 两次应答），唯独音频记录没建出来——bluealsa 端点注册了，但 **A2DP 的 SDP 服务记录就是没生成**（BlueZ 5.54 + -C 兼容模式的坑，不深究，绕过）。

**修复**：手动把 Audio Sink 记录写进 SDP 数据库：

```sh
sdptool add A2SNK      # 手动补 Audio Sink 记录
```

**固化**（bt_up.sh 第 6 步重写）：同时注册两类记录 + **服务自检循环**——

```sh
sdptool add --channel=3 SP
sdptool add A2SNK
# 自检循环：逐条查 Serial Port / Audio Sink，丢了自动补并打日志
```

### 第三幕验收（10-14，真机截图实锤）

手机删配对 → 重配 → 详情页出现「媒体音频」开关（开）→ 状态变为：

> **T113-KelpBar [SBC] 已连接 | 使用中（媒体）**

btmon 同窗确认：手机 `7C:A4:49:2C:A6:6D` 与电脑 `14:B5:CD:71:99:D8` **同时在线且 AUTH ENCRYPT**。

三个"看起来像坏了其实正常"的现象，别再当故障查：

| 现象 | 真相 |
|---|---|
| 已配对设备**不再出现在扫描列表** | 配对成功的正常表现，去「已配对设备」里找 |
| A2DP 空闲约 **31 秒自动断开** | 省电机制（btmon 实测 ACL 31s Disconnect），放歌时自动重连 |
| `/proc/asound/.../status` 显示 closed | A2DP 只在真正播放时开流 |

### 附：bluetoothd 挂掉后的完整重启序列（实测有效）

症状先行：`sdptool add` 报 `Failed to connect to SDP server ... Connection refused` = /var/run/sdp 套接字没了 = bluetoothd 没在跑。

```sh
killall bluetoothd bluealsa bluealsa-aplay 2>/dev/null
bluetoothd -n -C &                                # 1. 起 bluetoothd（-C 建 sdp 套接字）
# 2. 重启 bluealsa + aplay（start-stop-daemon -b，命令同层 3）
hciconfig hci0 piscan                             # 3. bluetoothd 重启会重置可发现性，必须补：

hciconfig hci0 class 0x240404                     #    COD 改音频/音箱类（让 Windows 建音频端点）
btmgmt name T113-KelpBar
sdptool add A2SNK                                 # 4. 重补 SDP 记录（add 重复无害）
sdptool add --channel=3 SP
```

> COD 为什么从 0x000104 改成 0x240404：配对时 COD=电脑类，**Windows 只给它挂 SPP 串口、不建音频端点**（蓝牙设置里看不到 Stereo）；改成音频/音箱类 + 删配对重配，Windows 才会枚举音频服务。

## 第四幕：A2DP 卡顿（带宽之战，最终解法）

### 4.1 定量诊断：先算账，再动手

**症状**：手机连上放歌，声音一卡一卡（整段断续，不是咔啦杂音——接触不良是杂音，数据饿死是断流，现象性质不同）。

**实测带宽**（板上命令，8 秒差值法）：

```sh
hciconfig hci0            # 记下 RX bytes，等 8 秒再记一次
# 两次差值 81,538 字节 ÷ 8 秒 ≈ 10.2 KB/s 实际到达速率
```

**需求侧算账**：SBC 立体声典型码率 328 kbps ÷ 8 ≈ **41 KB/s**。

| 项 | 数值 |
|---|---|
| UART1 理论带宽（115200 8N1） | 11.5 KB/s |
| UART1 **实测**到达 | **10.2 KB/s** |
| 立体声 SBC 需求 | **~41 KB/s** |
| 差距 | 管道只有需求的 **1/4** → 数据必然饿死 |

同时排除其他嫌疑：内核 overrun 计数、HCI 错误计数**均为 0**——驱动层无错，纯粹是管道容量问题。

**结论**：115200 的 UART 是瓶颈。要么提高管道速率，要么降低流量。先试前者（改芯片波特率），失败后走后者（压 SBC 码率）。

### 4.2 尝试 A：改芯片波特率 1.5M（编码正确，仍失败，最终放弃）

**思路**：rtl8723d_config 的 data[0:4] 写 1.5M（小端 `60 E3 16 00` = 0x0016E360 = 1,500,000），data[12] 清掉 bit2 硬件流控位（0x5F → 0x5B，因为 PG8/PG9 没接，见第 0 章）。

**结果**（日志原文）：

```
config baud rate to :16e360, hwflowcontrol:5b     ← rtk_hciattach 正确解析出了 1.5M 和新流控位
Get config baud rate from config file:16e360      ← 编码疑虑排除：解析没问题
3-wire download patch re send:1..40               ← 但固件补丁下载还是超时
H5 patch timed out
```

**假死循环**：每次失败芯片都进入假死（7 个波特率 115200/1.5M/921600/460800/250000/500000/576000 全扫无应答），每次都得断电 15 秒重来。

**为什么放弃**（有依据，不是怂）：
- 主机串口是否真切上了 1.5M 无法验证——板上 busybox **没有 stty**，hciconfig **不支持 speed 子命令**；
- sunxi UART 是整数分频：24M 时钟下 1.5M（N=1）恰好精确，**921600（N≈1.63）会偏 23%**，退档 921600 大概率更糟；
- 已烧掉大量断电重启周期，而方案 B（压码率）不依赖任何硬件改动。

**最终板上状态**：`/lib/firmware/rtlbt/` 回退为**无 config 文件**（115200 稳定路径），SDK 侧同步回退（md5 双端核对）。1.5M 补丁版留存 `08-bt/patches/` 备查。

> **这一幕的另一个事故与修复**（和每个人都有关）：
> 板上写文件（`/etc/bt_up.sh`）后**没执行 `sync` 就断电**，写入还在 page cache 没落 flash → 文件被清成 **0 字节**。rc.local 的 `[ -x ]` 检查对 0 字节文件照样通过 → `sh 空文件` 静默跳过蓝牙段 → 开机无蓝牙、无日志，排障半天。
> **两条铁律：① 板上写完文件必须 `sync`；② `/etc` 与 `/root` 双份互备，rc.local 里做路径回退。**

### 4.3 尝试 B（正路）：bluealsa 源码补丁，从协商层压住码率

**第一步：先读源码，别信参数名。**

`bluealsa --a2dp-force-mono` 看名字应该能强制单声道，实测 `channels: 2` 没效果。读源码实锤：`a2dp_codecs_init()` 里 force_mono 只修改 **source 端**（板子作音源）的 SEP，**sink 端**（板子作音箱，我们的场景）的 `a2dp_codec_sink_sbc` 能力声明**原封不动**——它只是给手机"多一个单声道选项"，手机照样选立体声。

**第二步：改 sink 端能力声明。**

源码：`src/a2dp.c`（bluez-alsa-20211122）。三处修改：

```c
/* ① 第 155 行附近：去掉 const，才能改成员 */
static struct a2dp_codec a2dp_codec_sink_sbc;   /* 原: static const ... */

/* ② a2dp_codecs_init() 的 force_mono 块内，sink 能力收窄为单声道 */
a2dp_codec_sink_sbc.capabilities.sbc.channel_mode = SBC_CHANNEL_MODE_MONO;

/* ③ max_bitpool 压到 10（第一版 12） */
a2dp_codec_sink_sbc.capabilities.sbc.max_bitpool = 10;
```

**为什么是 12 → 10（算账）**：

| bitpool | 单声道 44.1kHz 净载荷 | + RTP/L2CAP/H5 开销 ~2.7KB/s | 对 10.2KB/s 管道 |
|---|---|---|---|
| 12 | ~7.5 KB/s | ≈ 10.2 KB/s | **恰好顶满**，零星小卡 |
| **10** | ~6.3 KB/s | ≈ 8 KB/s | **留 20% 余量** → 流畅 |

A2DP 规范规定手机必须在 sink 广播的能力范围内选择——**sink 收窄后手机只能按低码率编码**，从协商源头压住流量，这才是根治。

**第三步：交叉编译配方**（VM 内，四步缺一不可）：

```bash
# ① 工具链进 PATH
export PATH=~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/toolchain/bin:$PATH
# ② wrapper 强制要求 STAGING_DIR（缺了直接 fatal error）
export STAGING_DIR=~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/target
# ③ Makefile 调短名 arm-openwrt-linux-gcc，工具链只有版本长名 → 补软链
ln -sf arm-openwrt-linux-gnueabi-gcc-8.3.0 \
       ~/T113-Tina5.0-V1.2/openwrt/openwrt/staging_dir/toolchain/bin/arm-openwrt-linux-gcc
# ④ 编译（只重编 a2dp.o + 链接，约 1 分钟）
cd ~/T113-Tina5.0-V1.2/out/t113/evb1_auto_nand/openwrt/build_dir/target/bluez-alsa-20211122 && make -C src
```

产物 `src/bluealsa`（158,272 字节）→ `vm_get_b64.py` 取回 Windows（本 VM sshd 无 SFTP，base64 走 exec 通道）→ adb 推板。

**第四步：部署**（一次 adb 搞定）：

```sh
adb push bluealsa_bp10 /usr/bin/bluealsa.new
adb shell "killall -9 bluealsa bluealsa-aplay
  mv /usr/bin/bluealsa.new /usr/bin/bluealsa && chmod 755 /usr/bin/bluealsa && sync
  start-stop-daemon -S -b -x /usr/bin/bluealsa -- -p a2dp-sink --a2dp-volume -i hci0 --a2dp-force-mono --sbc-quality=low
  start-stop-daemon -S -b -x /usr/bin/bluealsa-aplay -- --profile-a2dp 00:00:00:00:00:00
  sdptool add A2SNK; sdptool add --channel=3 SP"
```

**第五步：验证——只认协商层证据。**

改完能力声明不等于手机会用。**安卓会按设备缓存协商结果**：此时只是关开「媒体音频」开关，**不足以**让手机重读能力（实测 channels 依旧 2）。必须**重启手机蓝牙开关**（或删配对重配），手机才会重新发 GET_CAPABILITIES。

btmon 抓包验证（重连放歌）：

```
AVDTP: GET_CAPABILITIES → SET_CONFIGURATION
       Maximum Bitpool: 12        ← 第一版补丁协商成功实锤
       → Open → Start 全通过
```

> **验证边界（哪些算实锤，哪些是错觉）**：
> - 协商层（btmon 里的 AVDTP Set Configuration 的 Bitpool 值）= **唯一可信判据**；
> - ALSA `hw_params` 显示 channels: 2 **不作数**——bluealsa-aplay 固定开双声道 PCM，单声道流会被复制，这是播放端行为不是协商结果；
> - RX 速率顶格（10.2KB/s）**不作数**——bitpool 12 配置恰好也顶满管道，两种配置速率一样，区分不了；
> - 体感"好多了"**不作数**——只有 btmon 见到目标 Bitpool + 无卡顿才闭环。

### 4.4 收工状态

bitpool 10 版本部署、手机重启蓝牙重连放歌，**流畅，用户验收收工**。

最终链路（每一环都验证过）：

```
手机 ──A2DP/SBC(单声道,bitpool10)──> hci0 ──H5/UART1@115200──> bluealsa
  --> 声卡 audiocodec --> HPOUT --> LM4871 功放 --> CN2 喇叭
```

代价：音质降为"电话音质"档——**在 10.2KB/s 的管道里，这是流畅与音质的理性取舍**（退档阶梯：嫌闷可回 bitpool 12 接受零星小卡；bitpool 8 为最终保底）。
