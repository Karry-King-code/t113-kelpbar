## 第 1 部分：四个必须懂的概念

不看这部分，后面全是天书。**这部分我不想省，因为它是你面试时能讲出来的东西。**

### 概念1：BSP 三层结构 —— 出问题先问「改哪一层」

板子从上电到开机，是按顺序跑的：

| 层 | 名字 | 通俗理解 | 能不能改 |
|---|---|---|---|
| 第1层 | **boot0** | 芯片内部固化的第一段代码，负责初始化内存 | ❌ 闭源，改不了 |
| 第2层 | **U-Boot** | 引导程序，负责搬起内核、显示开机 logo | ✅ 可改，要重编 |
| 第3层 | **Kernel + 设备树** | 操作系统内核 + 硬件配置表 | ✅ 可改，要重编 |
| 第4层 | **rootfs** | 内核跑起来的"硬盘"内容 | ✅ **板上直接改，免重编免烧录** |

> ### ⭐ 本章最重要的一句话
> **出问题先问「改哪一层」，不要上来就重刷固件。**
>
> 本章最后的"彩条固化"，用的就是**第4层 rootfs** —— 在板子上直接改个文件，**不用编译、不用烧录**，两分钟搞定。

### 概念2：设备树（DTS）—— 硬件的"配置表"

内核怎么知道你的屏幕是 720×1424？靠一张**参数表**，叫**设备树**（Device Tree），文件后缀 `.dts`。

真实片段长这样：

```dts
&lcd0 {
	lcd_used        = <1>;              // 1 = 启用屏幕
	lcd_driver_name = "fl7707n_mipi";   // 用哪个屏幕驱动
	lcd_x           = <720>;            // 屏幕宽 720
	lcd_y           = <1424>;           // 屏幕高 1424
	...
};
```

> **关键理解**：设备树**不是代码，是参数表**。改分辨率、改引脚，都是改这张表，不用动 C 代码。

### 概念3：`/sys` 是什么 —— 内核的"控制面板"

Linux 内核把很多可调参数暴露成**文件**，放在 `/sys` 下。**读文件 = 看状态，写文件 = 改设置**。

```sh
cat /sys/class/disp/disp/attr/xres              # 读：屏幕宽 → 输出 720
echo 1 > /sys/class/disp/disp/attr/colorbar     # 写：打开彩条
```

> **注意**：写 `1` = 打开，写 `0` = 关闭。这是内核约定，不是随便定的。

### 概念4：rootfs 是「只读底座 + 可写白板」（overlayfs）

板子的文件系统是**两层叠起来**的：

```
     你看到的 /                ← 合并视图（看起来是一层）
          ↑ 叠加(overlay)
     ┌────┴─────────────────┐
     │ /overlay  (可写)      │  ← 你改的文件存这里，重启还在
     ├───────────────────────┤
     │ /rom  (squashfs 只读) │  ← 出厂固件底座，改不动
     └───────────────────────┘
```

**为什么必须懂这个？** 因为你要固化彩条，就得把文件写到**可写层 `/overlay`**。如果只改了内存里的东西，重启就没了。

**验证写进去了没**（后面第 4 部分会用到）：

```sh
ls -la /overlay/upper/etc/rc.local
```

> **看到这个文件 = 你的改动已经落盘，重启不丢。**

## 第 2 部分：诊断黑屏 —— 六层挖根（本章精华）

**这部分是整份文档最有价值的地方。** 它教你的不是"改哪一行"，而是一套**遇到任何显示问题都能用的排查方法**。

### 当时的症状

触摸任务做完后，屏幕还是黑的：

- 内核日志里明明有屏幕驱动 `fl7707n_mipi` 的字样
- 但屏幕就是不亮
- 反复调分辨率都没用

### ⭐ 排查方法总纲

嵌入式显示问题，**永远按这个顺序一层层剥**：

```
U-Boot 开屏?  →  内核接管?  →  屏幕驱动加载?  →  分辨率对不对?  →  背光开没开?
```

---

### 第1层：先确认「屏幕到底有没有被开过」

**在哪**：VM 终端
**敲什么**（假设你的串口日志文件叫 `serial.log`）：

```sh
grep -iE "lcd_open_flow|lcd_power_on|lcd_panel_init|lcd_bl_open" serial.log
```

**看到什么算对**：正常应该打印出一串：

```
=====================lcd_open_flow
=====================lcd_power_on
=====================lcd_panel_init
=====================lcd_bl_open
```

**我当时看到什么**：**这四行一行都没有**（grep 无输出）。

**这说明什么**：内核**根本没执行屏幕的打开流程**。屏幕驱动虽然被加载了，但"开屏动作"从没被调用。

> ❗**注意**：这里容易读错。是"**一行都没打印**"（grep 无输出），**不是**"打印了 lcd_open_flow"。
> 文档早期版本把这点写反了，会让复刻者彻底懵，特此更正。

---

### 第2层：为什么内核不执行？—— 找到 `smooth display`

**在哪**：VM 终端
**敲什么**：

```sh
grep -i "smooth display" serial.log
```

**我看到的**：

```
smooth display screen:0 type:1 mode:4
```

**这句话什么意思**：`smooth display` = **"平滑显示"**。它的含义是：

> "U-Boot 那边已经把屏幕开好了，内核你就别重复开了，直接接手就行。"

内核一看这个标记，就把整个屏幕初始化流程**跳过了**。

> **于是问题的性质变了**：
> 不是"内核开不了屏"，而是"**内核认为 U-Boot 已经开了，所以它不开**"。

---

### 第3层：那 U-Boot 到底开没开？

**在哪**：VM 终端
**敲什么**（U-Boot 日志在串口最前面 0~2 秒那段）：

```sh
grep -iE "LCD open finish|boot_gui_init|disp_devices_open" serial.log
```

**我看到的**：

```
[01.161]LCD open finish
```

**结论**：U-Boot **确实开屏了**，而且用的是它自己配置表里的（**错误的**）参数。

**黑屏的直接原因**：U-Boot 用错误参数占住了屏幕，内核又"礼貌地"不去碰，两边不接力 → 屏幕黑。

---

### 第4层：想关掉 U-Boot 开屏 —— 第一个陷阱

**我一开始的想法**（很自然，但错了）：

> U-Boot 配置表里把 `lcd_used` 改成 0，它不就不开屏了吗？

**结果**：改了，重编，烧录 → **没用，屏幕还是黑**。

**为什么？** 因为 `lcd_used` 在 U-Boot 里**根本不是开关**。它只被一个叫 `drv_disp_check_spec()` 的函数用来**校验分辨率是否合法**。你把它关掉，U-Boot 该开屏还是开屏。

> ### ⭐ 金句
> **名字骗人，要去代码里看它到底被谁用。**
> `lcd_used` 听起来像开关，实际上只是个"参数合法性检查的输入"。

### 第5层：真正的开关 —— `CONFIG_BOOT_GUI`

既然改配置表没用，那就去**代码**里找"到底谁调用了开屏"。

**在哪**：VM 终端
**敲什么**：

```sh
cd ~/T113-Tina5.0-V1.2/brandy/brandy-2.0/u-boot-2018
grep -rn "board_bootlogo_display" --include=*.c | head
```

**顺着找到的调用链**（一层层往上追）：

```
board_env_late_init()               ← 启动环境初始化
    └─> #ifdef CONFIG_BOOT_GUI      ← ★被这个编译宏包着
            board_bootlogo_display()    ← 显示开机 logo
                └─> boot_gui_init()         ← 初始化图形界面
                        └─> disp_devices_open()  ← 打开显示设备 ★真凶
```

> **答案浮出水面**：只要 `CONFIG_BOOT_GUI` 打开，U-Boot 就**无条件开屏**，跟 `lcd_used` **一点关系都没有**。

#### 怎么关掉它（可复制的完整操作）

**在哪**：VM 终端

**① 先看现状**：

```sh
cd ~/T113-Tina5.0-V1.2/brandy/brandy-2.0/u-boot-2018
grep -n "CONFIG_BOOT_GUI" configs/sun8iw20p1_auto_defconfig
grep -n "CONFIG_BOOT_GUI" .config
```

**我看到的输出**（已核实，2026-10-09）：

```
196:# CONFIG_BOOT_GUI is not set          ← defconfig 第 196 行
995:# CONFIG_BOOT_GUI is not set          ← .config 第 995 行
```

**② 判断现在是什么状态**：

| 你看到的 | 含义 | 要做什么 |
|---|---|---|
| `# CONFIG_BOOT_GUI is not set` | **已经是关闭的** | 不用改，直接跳到第6层 |
| `CONFIG_BOOT_GUI=y` | **打开的**（真凶还活着） | 执行下面第 ③ 步 |

**③ 如果是打开的，改成关闭**（改两个文件，都要改）：

```sh
cd ~/T113-Tina5.0-V1.2/brandy/brandy-2.0/u-boot-2018

# 先备份
cp configs/sun8iw20p1_auto_defconfig configs/sun8iw20p1_auto_defconfig.bak-bootgui
cp .config .config.bak-bootgui

# 把 y 改成 not set
sed -i 's/^CONFIG_BOOT_GUI=y/# CONFIG_BOOT_GUI is not set/' configs/sun8iw20p1_auto_defconfig
sed -i 's/^CONFIG_BOOT_GUI=y/# CONFIG_BOOT_GUI is not set/' .config

# 验证：两处都应该显示 is not set
grep -n "CONFIG_BOOT_GUI" configs/sun8iw20p1_auto_defconfig .config
```

> **为什么两个文件都要改？**
> `configs/sun8iw20p1_auto_defconfig` 是"**出厂默认配置模板**"（会被 `mkconfig` 读取）；
> `.config` 是"**当前生效的配置**"（编译真正读的）。
> 只改一个，下次编译可能被另一个覆盖回来。

> **为什么是 `sun8iw20p1_auto_defconfig` 这个名字？**
> 因为 build 日志会打印实际用的 defconfig 名。核对你自己的：
> ```sh
> grep -i "defconfig" ~/T113-Tina5.0-V1.2/out/*/compile.log 2>/dev/null | head -3
> ```

#### ★ 怎么证明"真的关掉了"（重要）

**硬证据 = 镜像体积变小**。

关掉 `CONFIG_BOOT_GUI` 后，编译出来的镜像比上一版**小了 32KB**：

| 镜像 | 大小 |
|---|---|
| 关之前 | 21,552,128 字节 |
| 关之后（`v5_nogui`） | 21,519,360 字节 |
| **差值** | **32,768 字节 = 32KB** |

> **那 32KB 就是被裁掉的 GUI 代码。**
> **"体积变小"= "代码真的被裁掉了"的物证。** 这是可验证的，不是猜的。

### 第6层：闪屏一下变黑 —— fb 尺寸对不上

U-Boot 不开屏之后，屏幕**闪了一下就黑了**。新症状 = 说明内核开始接管了，但出了新问题。

**诊断**：搜日志发现内核报的分辨率是 **1024×600**，而屏幕实际是 **720×1424**。

**为什么内核认为是 1024×600？** 因为**内核设备树里的 framebuffer 尺寸没改**（还是出厂默认的）。

#### 怎么读设备树里的值（在板子上读）

**在哪**：Windows 终端
**敲什么**：

```sh
D:\t113_work\flash_tools\adb.exe shell "ls /proc/device-tree/disp@5000000/"
```

先看有哪些属性文件，然后读具体的：

```sh
D:\t113_work\flash_tools\adb.exe shell "xxd /proc/device-tree/disp@5000000/fb0_width"
D:\t113_work\flash_tools\adb.exe shell "xxd /proc/device-tree/disp@5000000/fb0_height"
```

> ### ★ 知识点：设备树里的数字是**大端序**（Big-Endian）
>
> `xxd` 读出来是原始字节，要按**大端**解释：
>
> | 读到 | 计算 | 结果 |
> |---|---|---|
> | `00 00 04 00` | 0x0400 | **1024** ← 出厂 LVDS 遗留值 |
> | `00 00 02 58` | 0x0258 | **600** ← 出厂 LVDS 遗留值 |
> | `00 00 02 D0` | 0x02D0 | **720** ✅ 我们改对的 |
> | `00 00 05 90` | 0x0590 | **1424** ✅ 我们改对的 |
>
> **我最初读错了**：用 `hexdump` 按小端读，`lcd_x` 显示成 `-805175296`（负数）。
> **教训**：读 `/proc/device-tree` 的值，要么用 `xxd` 看原始字节手算，要么明确知道是大端。

#### 怎么改（VM 里改文件）

**在哪**：VM 终端
**改哪个文件**：

```
~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand/linux-5.4/board.dts
```

> ### ⚠️⚠️ 极其重要的坑：`board.dts` 是**符号链接**
>
> `device/config/chips/t113/configs/evb1_auto_nand/board.dts` 是一个**软链接**，
> 指向 `linux-5.4/board.dts`。
>
> **如果用 `sed -i` 改软链接会怎样？**
> GNU 的 `sed -i` 会**销毁软链接**，在原地生成一个**普通文件**。
> 结果：
> - 你 `cat` 验证时读的是**新建的那个文件**（改动在，看起来成功）
> - 但 `./build.sh` 编译时，构建脚本发现布局被破坏，会**删掉它、重建软链接**，指回原始版本
> - **编译永远读的是原版** → 改动永远上不了板
>
> **一句话**：**验证和编译读的是两个文件，平行线永不相交。**
> （这个坑当时坑了整整两轮调试，是本章最大教训之一）
>
> **正确做法**：
> 1. **要么** 直接改**真身**（`linux-5.4/board.dts`）—— 推荐
> 2. **要么** 用 Python 脚本改（Python 的 `open()` 会穿透软链接）
> 3. **绝对不要** 用 `sed -i` 改软链接

**先确认真假身**：

```sh
cd ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand
ls -la board.dts
```

如果输出第一个字符是 `l`（如 `lrwxrwxrwx`），那就是软链接：

```
lrwxrwxrwx 1 karry karry 19 ... board.dts -> linux-5.4/board.dts
```

**所以直接改真身**：

```sh
cd ~/T113-Tina5.0-V1.2/device/config/chips/t113/configs/evb1_auto_nand

# 备份真身
cp linux-5.4/board.dts linux-5.4/board.dts.bak-display

# 找到要改的地方
grep -n "fb0_width\|fb0_height\|fb0_format" linux-5.4/board.dts
```

**改成这样**（用编辑器或 Python 脚本）：

```dts
fb0_format = <0>;
fb0_width  = <720>;      // ← 必须等于 lcd_x
fb0_height = <1424>;     // ← 必须等于 lcd_y
```

**改完立即验证**：

```sh
grep -n "fb0_width\|fb0_height" linux-5.4/board.dts
ls -la linux-5.4/board.dts          # mtime 应该是刚刚
```


验证：

```sh

```

**② 改 `<DISP>/lcd/Kconfig`**

加一个配置项：

## 第 4 部分：让彩条在「复位后自动回来」

### 问题

彩条是用 `echo 1` 打开的，**重启就没了**。

**为什么？** 因为 `echo 1 > /sys/...` 改的是**内核内存里的一个变量**，不是磁盘文件。掉电/重启，内存清零，变量回默认值。

### 解决思路

Linux 开机时会按顺序执行一堆初始化脚本，**最后一个**（`S95done`）会调用 `/etc/rc.local`。

**`/etc/rc.local` 的官方说明**（板子上原文）：

```sh
# Put your custom commands here that should be executed once
# the system init finished. By default this file does nothing.
```

翻译：**"系统初始化完成后要执行的命令，写这儿。默认啥也不干。"**

**这就是官方指定的"开机自启"位置。**

### 为什么挂在 rc.local 是安全的（时序论证）

**担心**：rc.local 跑的时候，屏幕驱动起来了没？

**证据**：查内核日志里 disp 驱动的初始化时间：

```
[    2.034914] =====================lcd_bl_open
[    2.039951] [DISP] disp_device_attached_and_enable,line:226
```

**第 2.03 秒**屏幕驱动就初始化完了。而 `S95done` 是**所有 init 脚本里最后一个**，执行时间肯定晚于 2 秒。

> **结论：时序安全，不存在"跑太早"的问题。**
>
> **记住这个套路**：任何"开机自启不生效"，第一个查**时序** —— 你的命令执行时，它依赖的东西准备好了吗？

```sh
# the system init finished. By default this file does nothing.

amixer cset name="HPOUT Switch" 1

# capture
amixer -Dhw:audiocodec cset name='MIC3 Input Select' 1
amixer -Dhw:audiocodec cset name='MIC3 Switch' 1
amixer -Dhw:audiocodec cset name='ADC3 Gain' 19
```

```sh
        break
    fi
    sleep 1
done
echo 1 > /sys/class/disp/disp/attr/colorbar

exit 0
```

**逐行解释**（新增的部分）：

| 行 | 作用 |
|---|---|
| `for i in 1 2 3 4 5; do` | 最多循环 5 次 |
| `if [ -e /sys/class/disp/disp/attr/colorbar ]; then break; fi` | **属性文件存在就跳出**（防御性：万一驱动慢，等它） |
| `sleep 1` | 每轮等 1 秒，最多等 5 秒 |
| `echo 1 > /sys/class/disp/disp/attr/colorbar` | **正式打开彩条** |

> **为什么要写这个 `for` 循环？**
> 万一以后换屏、驱动加载更慢，直接 `echo` 会失败。加上等待逻辑，脚本**更健壮**。这是"防御性编程"的习惯。

## 第 8 部分：常考问题

**Q1：为什么内核不初始化屏幕？**
A：因为 U-Boot 已经开屏并设置了 `boot_info.sync`，内核看到这个标记就走 `smooth display`（平滑显示）路径，跳过整个 panel 初始化流程。

**Q2：`lcd_used` 为什么不起作用？**
A：在 U-Boot 里它只被 `drv_disp_check_spec()` 用于分辨率合法性校验，**不是开屏开关**。真正的开关是编译宏 `CONFIG_BOOT_GUI`，它控制 `board_bootlogo_display()` 是否被编译进去。

**Q3：怎么证明真的关掉了那个功能？**
A：**镜像体积变小 32KB** —— 被裁掉的 GUI 代码就是这 32KB。这是可验证的物证，不是猜的。

**Q4：为什么彩条重启会丢？**
A：`echo 1 > /sys/class/disp/disp/attr/colorbar` 修改的是内核内存里的变量，不是磁盘文件。掉电后内存清空，变量回到默认值。

**Q5：怎么让它在重启后自动显示？**
A：写进 `/etc/rc.local`。系统初始化最后一步 `S95done` 会 `sh /etc/rc.local`。因为 disp 驱动在 2.03 秒就准备好了，而 rc.local 执行得更晚，**时序安全**。

**Q6：屏幕驱动的注册为什么要改 4 个地方？**
A：①`Makefile` 决定**要不要编译**这个 .c 文件；②`Kconfig` 提供**配置开关**；③`panels.c` 把驱动**挂进 panel 列表**（内核靠这张表找驱动）；④`panels.h` 提供**声明**（否则 panels.c 编译不过）。四者缺一不可。
